# SDT, runtime, IR and optimization: derivations

## Evaluation order of an SDD: the dependency graph
<!-- topics: cd-sdt-ir-optimization.sdd-attributes, cd-sdt-ir-optimization.s-l-attributed -->

**Claim.** Fix a parse tree and an SDD. Build the dependency graph $G$: one node per attribute instance at each tree node, and an edge $a \to b$ whenever the semantic rule that defines $b$ reads $a$. Then the attributes of the tree can be evaluated, each rule run once after all of its inputs, if and only if $G$ is acyclic, and in that case every topological order of $G$ is a valid evaluation order. A synthesized attribute of a node $N$ is defined by a rule of the production at $N$ and reads only $N$ and its children; an inherited attribute of $N$ is defined by a rule of the production at $N$'s parent and reads the parent, $N$'s siblings and $N$. Terminals carry only synthesized attributes, supplied by the lexer (num.lexval), so their attributes have no incoming edges in $G$.

**Proof.** An evaluation order is a sequence of all the attribute instances in which each instance comes after every instance its rule reads, which is exactly a linear order of the nodes of $G$ in which every edge points forward: a topological order. If $G$ is acyclic a topological order exists (Kahn's algorithm: repeatedly remove a node with no incoming edges; an acyclic finite graph always has one), so evaluation succeeds. If $G$ has a cycle $a_1 \to a_2 \to \dots \to a_k \to a_1$, any order must place $a_1$ before $a_2$ before … before $a_k$ before $a_1$, which is impossible, so no order exists. Nothing in the argument depends on which topological order is chosen, so all of them compute the same values; the rules are functions of their inputs only. The split between synthesized and inherited attributes fixes the direction of information flow: synthesized edges point up the tree, inherited edges point down or sideways, and only the inherited ones can create sideways or downward dependence that a single bottom-up pass cannot honour.

**GATE use.** Questions ask for a valid evaluation order, whether an order is a topological sort of a drawn graph, or which rule makes the SDD circular. The trap is treating the SDD as a program run top to bottom; an SDD fixes only what each attribute equals, and the dependency graph alone fixes the order. A second trap is calling an attribute inherited because it appears on the right side of a rule; the kind is decided by which symbol the rule defines.

**Check.** Take $T \to F\,T'$ with $T'.\mathit{inh} = F.\mathit{val}$, $T' \to {*}\,F\,T'_1$ with $T'_1.\mathit{inh} = T'.\mathit{inh} \times F.\mathit{val}$ and $T'.\mathit{syn} = T'_1.\mathit{syn}$, $T' \to \varepsilon$ with $T'.\mathit{syn} = T'.\mathit{inh}$, and $T.\mathit{val} = T'.\mathit{syn}$. For `3 * 5 * 2` the graph has 10 attribute instances and 9 edges; a topological sort evaluates the inherited chain $3, 15, 30$ down the right spine, copies $30$ back up the synthesized chain, and gives $T.\mathit{val} = 30$. The two-rule SDD $A.s = B.i$, $B.i = A.s + 1$ has no node without an incoming edge, so it has no evaluation order.

## S-attributed and L-attributed SDDs evaluate in one pass
<!-- topics: cd-sdt-ir-optimization.s-l-attributed -->

**Claim.** (a) An S-attributed SDD (only synthesized attributes) can be evaluated during an LR parse by computing the head's attributes at each reduction. (b) An L-attributed SDD can be evaluated by one depth-first, left-to-right traversal, computing each child's inherited attributes just before visiting it and the node's synthesized attributes just after its last child. Here L-attributed means: for every production $A \to X_1 X_2 \cdots X_n$, each inherited attribute of $X_i$ reads only inherited attributes of $A$, attributes of $X_1, \dots, X_{i-1}$, and attributes of $X_i$ itself in a way that forms no cycle; synthesized attributes of $A$ may read anything in the production. The one-pass result in (b) needs the self-reads of $X_i$ to be of inherited attributes of $X_i$ only. The textbook definition (Aho, Lam, Sethi and Ullman, §5.2.4) also lets an inherited attribute of $X_i$ read a synthesized attribute of $X_i$, and that case is outside (b): with $A \to B$, $B.i = B.s$ and $B \to b$, $B.s = b.\mathit{lexval}$, the graph is acyclic, but the traversal must know $B.i$ before entering $B$ and learns $B.s$ only on leaving it. GATE questions never hinge on this case. (c) Every S-attributed SDD is L-attributed. An L-attributed SDD that defines at least one inherited attribute is not S-attributed, so the converse fails.

**Proof.** (a) Keep the attribute values of each grammar symbol on the parser stack beside the symbol. When the parser reduces by $A \to X_1 \cdots X_n$, the top $n$ entries are exactly $X_1, \dots, X_n$ with their values already computed: terminal values came from the lexer on shift, and nonterminal values were computed when those nonterminals were themselves produced by earlier reductions. A synthesized rule of $A$ reads only these, so it can run now; pop $n$ entries and push $A$ with its value. Induction on the number of reductions keeps the invariant "every stack entry holds its final attribute values".

(b) Define $\mathrm{visit}(N)$: for $i = 1, \dots, n$, compute the inherited attributes of $X_i$ and call $\mathrm{visit}(X_i)$; then compute the synthesized attributes of $N$. The invariant is: when $\mathrm{visit}(N)$ starts, $N$'s inherited attributes are known, and when it returns, every attribute in $N$'s subtree is known. The inputs of $X_i$'s inherited rules are inherited attributes of $N$ (known on entry), attributes of $X_1, \dots, X_{i-1}$ (their subtrees were completed by the earlier calls), or other inherited attributes of $X_i$, which are acyclic among themselves, so they can be computed in a topological order of those few dependencies before $\mathrm{visit}(X_i)$ starts. So each rule's inputs exist when it runs. After the loop, all children are complete, so $N$'s synthesized rules can run, which re-establishes the invariant. The order is exactly the order in which a recursive-descent or LL(1) parser expands and finishes nonterminals, which is why the traversal can be folded into such a parser.

(c) An S-attributed SDD has no inherited attributes, so the L condition, which constrains only inherited attributes, holds vacuously. A rule $B.i = C.s$ in $A \to B\,C$ reads a right sibling, which the traversal has not visited yet, and a rule $B.i = A.s$ reads a synthesized attribute of the parent, which is computed only after all children; either one breaks the L property.

**GATE use.** The MSQ gives a few productions with rules and asks which of S-attributed, L-attributed or neither apply. Classify each rule by its target: a rule defining the head's attribute is synthesized and never disqualifies L. For each inherited target $X_i$, check that every input is the head's inherited attribute or sits to the left. The trap is rejecting $A.s = B.s + C.s$ because it "uses a right symbol": synthesized rules may read every child.

**Check.** A classifier run on $A \to B\,C$: $A.s = B.s + C.s$ is S; $C.i = B.s$ with $A.s = C.s$ is L but not S; $C.i = A.i + B.s$ is L; $B.i = C.s$ is neither (right sibling); $B.i = A.s$ is neither (parent's synthesized). The depth-first evaluation of `3 * 5 * 2` from the previous section computes the inherited chain on the way down and returns 30 in one traversal.

## Postfix SDT actions run in postorder, and the grammar fixes precedence
<!-- topics: cd-sdt-ir-optimization.sdt-traces -->

**Claim.** Under a bottom-up (shift-reduce) parse, the reductions happen in the postorder of the parse tree: every node is reduced after all of its children, and the subtree of $X_i$ is reduced completely before any reduction inside the subtree of $X_{i+1}$. So with every action at the right end of its production (a postfix SDT), the actions run, and print, in postorder. In a grammar with one nonterminal per precedence level, an operator introduced at a deeper level binds tighter, and a left-recursive production $E \to E \mathbin{\mathrm{op}} T$ makes op left-associative ($E \to T \mathbin{\mathrm{op}} E$ makes it right-associative). An action in the middle of a body runs once the symbols to its left are recognised; a bottom-up parser does this by replacing the action with a marker $M \to \varepsilon$ carrying it.

**Proof.** A shift-reduce (LR) parser traces a rightmost derivation in reverse: each reduction undoes one step of it, the last step first. So it suffices to show that a rightmost derivation expands the tree in preorder with children taken right to left; reversing that order gives postorder with children left to right. A node's nonterminal must be in the sentential form before it is replaced, so a node is expanded before its children, and reduced after them. For siblings, after $A \to X_1 \cdots X_n$ is expanded, every symbol derived from $X_{i+1}$ lies to the right of every symbol derived from $X_i$. A rightmost derivation always replaces the rightmost nonterminal, so while any nonterminal remains in $X_{i+1}$'s part, nothing in $X_i$'s part is replaced: the whole subtree of $X_{i+1}$ is expanded before any step inside the subtree of $X_i$, the expansion of $X_i$ included. Reversed, every reduction inside $X_i$'s subtree comes before every reduction inside $X_{i+1}$'s. The argument never mentions tokens, so it covers a sibling that derives the empty string, such as a marker $M \to \varepsilon$: $M$ is reduced after all of $X_i$'s subtree and before anything inside the sibling to its right. Children first, left to right, parent last: that is postorder.

For precedence, in $E \to E \mathbin{\#} T \mid T$, $T \to T \mathbin{\&} F \mid F$, an `&` can only appear inside a $T$, so every `&` node is a descendant of the `#` nodes above it: `&` is applied first, it binds tighter. In $E \to E \mathbin{\#} T$ the left operand is an $E$ that can itself contain `#`, while the right operand $T$ cannot contain an unparenthesised `#`, so `a # b # c` must parse as `(a # b) # c`. A mid-body action $A \to \alpha\,\{a\}\,\beta$ becomes $A \to \alpha\,M\,\beta$ with $M \to \varepsilon\,\{a\}$; $M$ is reduced exactly when $\alpha$ is on the stack and before any token of $\beta$ is shifted, which is the required moment. The marker can add LR conflicts, which is why such schemes are not always parsable bottom-up.

**GATE use.** The 2-mark MCQ gives a grammar with odd operator symbols and print or value actions, then asks for the output or the value of an input string. Draw the parse tree from the grammar, then read the actions in postorder. The trap is using arithmetic habit: if `#` means $\times$ at the top level and `&` means $+$ one level deeper, $+$ binds tighter. The second trap is printing a parent's action before its children's.

**Check.** With `#` as $\times$, `&` as $+$, `F → num {print num}` and the other actions printing their operator, `2 # 3 & 5` parses as $2 \times (3 + 5) = 16$ and prints `2 3 5 & #`; `2 & 3 # 5 & 1` gives $(2+3) \times (5+1) = 30$ and prints `2 3 & 5 1 & #`. For `8 - 3 - 2` the left-recursive grammar gives $(8-3)-2 = 3$ and the right-recursive one gives $8-(3-2) = 7$. A recursive-descent evaluator of each grammar confirms all four numbers.

## Activation records, access links and the two scoping rules
<!-- topics: cd-sdt-ir-optimization.activation-records, cd-sdt-ir-optimization.scoping -->

**Claim.** (a) Stack allocation of activation records is correct whenever no local outlives its activation, because procedure activations nest: if $q$ starts after $p$ starts and before $p$ ends, then $q$ ends before $p$ ends. Recursion to depth $d$ keeps $d$ records of the procedure on the stack, using $d$ times the frame size. Static allocation, one fixed record per procedure, cannot support recursion. (b) With static scoping and nested procedures, let each frame's access link point to the most recent frame of the procedure that textually encloses it. Code at nesting depth $n_p$ reaches a name declared at depth $n_d \le n_p$ by following $n_p - n_d$ access links. When a procedure at depth $n_p$ calls one at depth $n_q$, then $n_q \le n_p + 1$, and the callee's access link is found by following $n_p - n_q + 1$ links from the caller's frame. (c) With dynamic scoping a non-local name is resolved by following control links, the most recent active frame declaring the name wins.

**Proof.** (a) Calls and returns follow the activation tree: an activation ends only after every activation it started has ended, which is LIFO, so a stack holds exactly the live activations, and each needs its own record because each has its own locals. A recursive procedure at depth $d$ has $d$ activations live at once, so it needs $d$ distinct records, which a single static record cannot provide. If a local must outlive its call (a returned closure, a pointer to a local), popping the frame destroys it, and stack allocation fails.

(b) Induction on the call sequence. A procedure at depth $n$ is declared inside one at depth $n - 1$, so its access link goes to a depth $n - 1$ frame, the next one to depth $n - 2$, and so on: each link lowers the depth by exactly 1, and after $n_p - n_d$ links the frame at depth $n_d$ is reached, the frame of the enclosing procedure that declares the name. For the call, $q$ is visible from $p$ only if $q$ is declared in $p$ itself or in a procedure enclosing $p$, so $q$'s parent has depth $n_q - 1 \le n_p$, giving $n_q \le n_p + 1$. The caller reaches that parent's frame by following $n_p - (n_q - 1) = n_p - n_q + 1$ links, and stores the result as the callee's access link; this keeps the invariant. When $q$ is nested directly in $p$ the count is 0 and the link is the caller's own frame.

(c) Under dynamic scoping the binding is defined by the call stack, not the text. The control link points to the caller's frame, so walking control links visits the active frames from most recent to oldest, and the first frame declaring the name is the binding.

**GATE use.** Programs that print a value under static and under dynamic scoping are the common 2-mark NAT. Resolve every non-local name once per rule: static by text nesting, dynamic by the latest active declaration. Questions on frames ask what an activation record holds (return value, parameters, control link, access link, saved status with the return address, locals, temporaries), or for the stack space of a recursion. The trap is following control links for static scoping, or counting access links by the call depth instead of the nesting depth.

**Check.** Global `x = 10`; `p() { x = x + 5; }`; `q() { int x = 1; p(); print x; }`; call `q()`. Static: `p`'s `x` is the global, so `q` prints 1 and the global becomes 15. Dynamic: `p` finds `q`'s `x` first on the stack, so `q` prints 6 and the global stays 10. A simulation of both lookups reproduces (1, 15) and (6, 10). With `main` at depth 1 enclosing `p` at depth 2 enclosing `q` at depth 3, code in `q` reaches a `main` variable in $3 - 1 = 2$ hops; `q` calling `p` sets the new link after $3 - 2 + 1 = 2$ hops, which lands on `main`'s frame. `fact(5)` with base case `n == 1` has 5 frames live at its deepest point, 160 bytes at 32 bytes per frame.

## Parameter passing: value, reference, value-result, name and need
<!-- topics: cd-sdt-ir-optimization.parameter-passing -->

**Claim.** Model memory as cells. Call by value gives each formal a new cell initialised with the actual's value, and nothing is copied back. Call by reference binds the formal to the actual's own cell, so two formals bound to the same variable alias. Call by value-result gives each formal a new cell on entry and copies each formal back to its actual's cell on return, so with aliasing the last copy written wins. Call by name binds the formal to a thunk, the actual expression with the caller's environment, re-evaluated at every use, both for reading and for locating the cell to write. Call by need is call by name with the thunk's value memoised on first use, so the argument is evaluated at most once.

**Derivation.** Each mechanism is a choice of what the formal denotes. Under value it denotes a fresh cell, so writes to it touch no caller cell. Under reference it denotes the caller's cell, so every write is seen by every name for that cell during the call. Value-result behaves like value during the call and adds one write per formal at return; when two formals map to the same actual, both writes land in one cell and the order of the copies decides which value survives. Under name, the formal stands for an expression whose meaning can change as the callee runs: if the expression is `a[i]` and the callee changes `i`, later uses address a different element. Memoising the first evaluation turns name into need; the results agree with name whenever evaluating the argument has no side effects and its value does not change during the call.

**GATE use.** The question gives a short procedure and one call, and asks for the printed value under a named mechanism. Draw a table of cells and which name maps to which cell, run the body, then apply the copy-out for value-result in the stated order. The traps are ignoring aliasing when one variable is passed twice, applying copy-out in the wrong order, and evaluating a by-name argument once at the call.

**Check.** `x = 5; f(a, b) { a = a + 1; b = b + a; }`, called as `f(x, x)`. By value, `x` stays 5. By reference, `a` and `b` are `x`: `x` becomes 6, then $6 + 6 = 12$. By value-result, the copies are $a = 6$ and $b = 5 + 6 = 11$; copying out $a$ then $b$ leaves 11, copying $b$ then $a$ leaves 6. Call by name on `swap(i, a[i])` with `i = 1`, `a[1] = 2`, body `t = x; x = y; y = t`, sets `i = 2` and then writes `t = 1` into `a[2]`, leaving `a[1]` unchanged; by reference the address of `a[1]` is fixed at the call and the swap works. A by-name argument used three times is evaluated 3 times, and by need once. A cell-level simulation reproduces every value.

## Three-address code: temporaries and array addressing
<!-- topics: cd-sdt-ir-optimization.three-address-code -->

**Claim.** (a) Translating an expression tree with $k$ operator nodes, one fresh temporary per operator, emits exactly $k$ instructions and $k$ temporaries, in postorder. Writing the root's result straight into the target saves one temporary. (b) For a row-major array with index ranges $l_1..u_1$ and $l_2..u_2$, $n_2 = u_2 - l_2 + 1$ columns and element width $w$,

$$\mathrm{addr}(A[i][j]) = \mathrm{base} + \big((i - l_1)\, n_2 + (j - l_2)\big)\, w,$$

and column-major order swaps the roles: $\mathrm{base} + \big((j - l_2)\, n_1 + (i - l_1)\big)\, w$. (c) `if (B) S1 else S2` and `while (B) S` compile with jumps whose targets can be filled in later by backpatching, in one pass.

**Derivation.** (a) Three-address code allows at most one operator on a right side, so each operator node needs its own instruction, and each instruction's result must be named so that its parent can read it; the fresh-temporary scheme names it $t_m$. Children are translated before parents, because a parent's operands must exist, so the instructions come out in postorder. The root's result can be assigned to the target directly, which removes the last temporary and the copy $x = t_k$. Reusing a temporary once its value has been read lowers the count further, so the count a question wants depends on the rule it states.

(b) Row-major order stores row $l_1$ in full, then row $l_1 + 1$, and so on. Before element $(i, j)$ lie the $i - l_1$ complete rows, each holding $n_2$ elements, and then the $j - l_2$ elements of row $i$ to its left. Each element takes $w$ bytes, which gives the formula. In code, the offset goes into temporaries first: $t_1 = i \times n_2$, $t_2 = t_1 + j$, $t_3 = t_2 \times w$, $x = A[t_3]$ when the lower bounds are 0.

(c) For `if (B) S1 else S2`: the code of $B$ jumps to $L_1$ when true and to $L_2$ when false; $L_1$ starts $S_1$, which ends with `goto Lnext`; $L_2$ starts $S_2$. For `while (B) S`: label the test $L_b$, jump into the body when true and to $L_{\mathrm{next}}$ when false, and end the body with `goto Lb`. Backpatching keeps, for each boolean expression, the list of emitted jumps whose target is not yet known (truelist, falselist). Each jump is in exactly one list and its target is filled in once, when its label is emitted, so no second pass is needed.

**GATE use.** Count instructions or temporaries for an assignment, give the address of an element for a declared array, or count jumps in the translation of a loop. The trap in counting is reading off the number of operators wrongly; in addressing it is forgetting nonzero lower bounds or using the row count where the column count belongs.

**Check.** `x = a + b * c - d` has 3 operators, so fresh temporaries give `t1 = b * c; t2 = a + t1; t3 = t2 - d; x = t3`, 3 temporaries, and 2 if the last result goes straight into `x`. For `int A[10][20]` with $w = 4$ and base 1000, $A[3][5]$ is at $1000 + (3 \cdot 20 + 5) \cdot 4 = 1260$ with 0-based indices, and at $1000 + (2 \cdot 20 + 4) \cdot 4 = 1176$ for `A[1..10][1..20]`. A script that lays out the 200 elements one by one finds the same address.

## Quadruples, triples and indirect triples
<!-- topics: cd-sdt-ir-optimization.ir-representations -->

**Claim.** For a translation with $n$ instructions: quadruples store $4n$ fields (op, arg1, arg2, result) and refer to results by temporary names; triples store $3n$ fields and refer to a result by the position of the triple that computes it; indirect triples store the $3n$ fields plus a list of $n$ pointers giving the execution order. Reordering instructions is free for quadruples, breaks references for triples, and costs only a permutation of the pointer list for indirect triples.

**Derivation.** A quadruple names its result, and every later use mentions that name, so a use refers to the value, not to where the instruction sits: moving instructions leaves every reference valid as long as each definition still runs before its uses. The price is that each temporary is a symbol-table entry. A triple drops the result field; a use is written $(m)$, meaning "the value of triple $m$". Moving triple $m$ to a new position changes the meaning of every $(m)$, so every reference would have to be rewritten. Indirect triples keep triples fixed in their table, so $(m)$ always means the same triple, and put the execution order in a separate list of pointers; an optimizer permutes that list. The extra list costs $n$ pointers over plain triples, which is why indirect triples use more space than triples while keeping the reordering freedom of quadruples.

**GATE use.** Questions give an expression and ask for its quadruples or triples, the number of entries, or which form suits an optimizer that reorders code. The trap is giving triples a result field, or claiming that triples can be reordered freely.

**Check.** For `a = b * -c + b * -c` the quadruples are `(minus, c, , t1)`, `(*, b, t1, t2)`, `(minus, c, , t3)`, `(*, b, t3, t4)`, `(+, t2, t4, t5)`, `(=, t5, , a)`: 6 entries. The triples are `(0) minus c`, `(1) * b (0)`, `(2) minus c`, `(3) * b (2)`, `(4) + (1) (3)`, `(5) = a (4)`. With $b = 3$, $c = 4$ both forms evaluate to $-24$, and running the indirect-triple list in the order 2, 3, 0, 1, 4, 5 still gives $-24$. Field counts: 24 for quadruples, 18 for triples, 18 plus 6 pointers for indirect triples.

## Static single assignment: renaming and φ-functions
<!-- topics: cd-sdt-ir-optimization.ssa -->

**Claim.** In straight-line code, conversion to SSA gives each assignment a fresh version of its target and renames every use to the most recent version, which preserves the meaning. The program then uses exactly $A + R$ variable names, where $A$ is the number of assignments and $R$ the number of variables read before (or without) being assigned, which keep their original names. Where control paths merge with different versions of $x$ reaching the join, a φ-function $x_k = \phi(x_i, x_j)$ at the join selects the version from the edge actually taken.

**Proof.** Process the statements in order and keep, for each variable, its current version. A use of $x$ in the original code reads the value of the most recent assignment to $x$ before it, or the input value if there is none. The renamed use reads the current version, which is by construction the name given to that most recent assignment, or the original name if no assignment has occurred. So every use reads the same value as before. Each assignment introduces one name, which gives $A$ names, and each variable read before its first assignment contributes its original name once, which gives $R$ more; nothing else is named. At a join, a use after the join reads whichever definition ran on the path taken, and a single name cannot denote two definitions, so a new definition is needed whose value depends on the incoming edge, which is what φ provides. Because every name now has one definition, the definition reaching a use is found by name, so use-def chains are explicit and constant propagation, dead-code elimination and value numbering work by looking up one definition.

**GATE use.** The NAT asks for the minimum number of total variables after converting a short straight-line block to SSA. The trap is counting only the new versions and leaving out the inputs that are read but never assigned, or giving a reassigned variable's original name an extra slot when it was never read before its first assignment.

**Check.** The block `x = u - t; y = x * v; x = y + w; y = t - z; y = x * y` becomes `x1 = u - t; y1 = x1 * v; x2 = y1 + w; y2 = t - z; y3 = x2 * y2`. There are 5 assignments and 5 read-only inputs $u, t, v, w, z$, so 10 variables; $x$ and $y$ are assigned before they are read, so their original names never appear. A renaming script produces the same code and the count 10. After `if (p) x = 1 else x = 2`, the join needs $x_3 = \phi(x_1, x_2)$.

## Basic blocks, the flow graph, dominators and natural loops
<!-- topics: cd-sdt-ir-optimization.basic-blocks-cfg -->

**Claim.** (a) Mark as leaders the first instruction, every jump target, and every instruction right after a jump; cutting the code before each leader gives exactly the basic blocks, so the number of blocks equals the number of leaders. (b) The flow graph has an edge $B \to C$ for each jump target of $B$'s last instruction and a fall-through edge to the next block when $B$ does not end in an unconditional `goto`, a return or a halt. Edges are distinct pairs of blocks, so a conditional jump whose target is the next block contributes one edge. (c) With every node reachable from the entry,

$$\mathrm{Dom}(n) = \{n\} \cup \bigcap_{p \in \mathrm{pred}(n)} \mathrm{Dom}(p), \qquad \mathrm{Dom}(\mathrm{entry}) = \{\mathrm{entry}\},$$

and iterating from $\mathrm{Dom}(n) = $ all nodes converges to the dominator sets. (d) An edge $n \to h$ is a back edge when $h \in \mathrm{Dom}(n)$; its natural loop is $h$ plus all nodes that can reach $n$ without passing through $h$.

**Proof.** (a) A piece from a leader up to the next leader has no jump into its middle, since every jump target is a leader, and no jump out of its middle, since a jump makes the next instruction a leader, so a jump can only be a piece's last instruction. So each piece is entered only at its first instruction and left only at its last. It is maximal: the next piece begins with a leader that is either a jump target, so it can be entered from elsewhere, or follows a jump, so control may not flow into it from above; either way the two pieces cannot be merged.

(b) Control leaves a block only at its last instruction, so its successors are that instruction's possible next instructions: the jump target, plus the next instruction unless the last instruction is an unconditional jump, a return or a halt. When the target is the next instruction both cases name the same block, so the edge is counted once.

(c) Every path from the entry to $n \neq \mathrm{entry}$ enters $n$ from some predecessor $p$. A node $D \neq n$ lies on every such path exactly when it lies on every path to every predecessor, that is, when $D \in \mathrm{Dom}(p)$ for all $p$. Adding $n$ itself, which trivially dominates $n$, gives the equation. For the iteration, two directions are needed. First, every iterate contains the true sets: this holds for the full starting sets and for $\{\mathrm{entry}\}$, and if $\mathrm{Dom}(p) \subseteq S(p)$ for every $p$ then $\mathrm{Dom}(n) = \{n\} \cup \bigcap_p \mathrm{Dom}(p) \subseteq \{n\} \cup \bigcap_p S(p)$, so an update never removes a true dominator. The sets only shrink and are finite, so the iteration stops, at some solution $S$ of the equations. Second, every solution $S$ is contained in the true sets. Take $D \in S(n)$ and any path $\mathrm{entry} = v_0, v_1, \dots, v_m = n$. Walk it backwards: if $D \ne v_m$, the equation at $v_m$ puts $D$ in $S(p)$ for every predecessor $p$, in particular in $S(v_{m-1})$; repeat. If the walk reached $v_0$ without meeting $D$, then $D \in S(\mathrm{entry}) = \{\mathrm{entry}\} = \{v_0\}$, a contradiction. So $D$ lies on every path from the entry to $n$, and $D$ dominates $n$. With both directions, the iteration stops at exactly the dominator sets.

(d) If $h$ dominates $n$, every path into $n$ passes $h$, so the edge $n \to h$ returns to a point that control had to pass through: a loop with the single entry $h$. Walking predecessors backwards from $n$ and stopping at $h$ collects exactly the nodes that can reach $n$ inside the loop; none of them can be entered from outside except through $h$, because $h$ dominates them.

**GATE use.** The 1-mark NAT asks for the number of basic blocks, or of flow-graph edges, of a short three-address program. Mark leaders, count them, then add edges per block. The trap is forgetting that the instruction after a conditional jump is a leader even when nothing jumps to it, or ending a block at a label instead of just before it. Loop questions ask for back edges or the nodes of a natural loop.

**Check.** The program `1: i = 1`, `2: j = 1`, `3: t1 = 10 * i`, `4: t2 = t1 + j`, `5: a[t2] = 0`, `6: j = j + 1`, `7: if j <= 10 goto 3`, `8: i = i + 1`, `9: if i <= 10 goto 2`, `10: i = 1`, `11: t5 = i - 1`, `12: a[t5] = 1`, `13: i = i + 1`, `14: if i <= 10 goto 11` has leaders 1, 2, 3, 8, 10, 11, so 6 blocks $B_1, \dots, B_6$, and 8 edges: $B_1 B_2$, $B_2 B_3$, $B_3 B_3$, $B_3 B_4$, $B_4 B_2$, $B_4 B_5$, $B_5 B_6$, $B_6 B_6$. The dominator iteration settles after 2 passes with $\mathrm{Dom}(B_k) = \{B_1, \dots, B_k\}$. The back edges are $B_3 \to B_3$, $B_4 \to B_2$ and $B_6 \to B_6$, and the natural loop of $B_4 \to B_2$ is $\{B_2, B_3, B_4\}$. A script that applies the leader rules, builds the graph and iterates the dominator equation reproduces all of this, and on 832 random reachable graphs of up to 7 nodes the iteration matches dominators found by deleting each node and testing reachability.

## The DAG of a basic block and common subexpressions
<!-- topics: cd-sdt-ir-optimization.dag -->

**Claim.** Build the DAG of a block statement by statement: a leaf $x_0$ for the initial value of each variable the first time it is read; for `x = y op z`, reuse an existing node with operator op and the same child nodes (for a commutative op, the same children in either order) and otherwise create one; then move the label $x$ to that node. After each statement, the node labelled $x$ computes $x$'s current value as a function of the initial values. Every node reused instead of created is a common subexpression eliminated. The block can then be rewritten with one instruction per interior node whose value is needed, plus one copy for each extra variable that is live on exit and labels the same node.

**Proof.** Invariant: after statement $k$, for each variable $x$, the node $\mathrm{cur}(x)$ denotes the value $x$ holds after statement $k$, and every node denotes a fixed function of the leaves. Initially no variable has been assigned, and the leaf $x_0$ denotes $x$'s initial value. For statement $k + 1$, `x = y op z`, the operand values are those of the nodes $\mathrm{cur}(y)$ and $\mathrm{cur}(z)$ by the invariant, so the value assigned to $x$ is op applied to those nodes. If a node with op and those exact children exists, it denotes the same function of the leaves, because the same operator applied to the same values gives the same value, so reusing it is sound. Moving the label to it updates $\mathrm{cur}(x)$, and no other variable's node changes. Matching must be by node, not by variable name: once $b$ is reassigned, `b + c` names a different node. A node all of whose labels have moved, and which no other node uses, computes nothing anyone needs, so it is dead. Emitting one instruction per needed interior node, in a topological order of the DAG, recomputes every live value once.

**GATE use.** The 2-mark NAT asks for the number of nodes, or of interior nodes, in the DAG of a block, or for the minimum number of instructions after common subexpression elimination. The trap is matching by names after a reassignment, which merges two different values, or forgetting the leaves when the question counts all nodes.

**Check.** `p = a + b; q = a + b; r = p * c; s = q * c; t = r - s; u = t + a` has leaves $a, b, c$ and interior nodes $+$ (labels $p, q$), $\times$ (labels $r, s$), $-$ and $+$: 7 nodes. `a = b + c; b = a - d; c = b + c; d = a - d` has leaves $b_0, c_0, d_0$, the node $+(b_0, c_0)$ labelled $a$, the node $-(a, d_0)$ labelled $b$ and $d$, and $+(-, c_0)$ labelled $c$: 6 nodes. The two occurrences of `b + c` are different values ($5$ and $4$ when $b, c, d = 2, 3, 4$), so they do not merge. The block shrinks to `a = b + c; d = a - d; c = d + c`, plus `b = d` if $b$ is live on exit. A DAG builder reproduces both counts.

## Strength reduction and loop-invariant code motion
<!-- topics: cd-sdt-ir-optimization.local-optimizations -->

**Claim.** (a) Let $i$ be a basic induction variable of a loop, changed only by one statement $i \leftarrow i + k$ that runs once per iteration, and let the statement $j = c\,i + d$ in the loop be the only definition of $j$ there, with loop-invariant $c$, $d$, $k$. Add a fresh variable $s$: put $s = c\,i_0 + d$ in the preheader, where $i_0$ is $i$'s value on entry, put $s \leftarrow s + c\,k$ right after the increment of $i$, and replace $j = c\,i + d$, where it stands, by the copy $j = s$. Then the new loop gives $j$ the same value as the original at every point, inside the loop and after it. Deleting the definition of $j$ and updating $j$ itself right after the increment is correct only when that definition already sat right after the increment. (b) A statement `x = y op z` whose operands are loop-invariant can be moved to the preheader when (1) no other statement in the loop assigns $x$, (2) every use of $x$ in the loop is reached only by this statement, and (3) its block dominates every loop exit at which $x$ is live (or $x$ is dead after the loop). The preheader is a new block on the edges entering the header from outside, so the moved code runs once per entry to the loop; the header runs on every iteration.

**Proof.** (a) Invariant: at every point of the loop, $s = c\,i + d$ for the current $i$. It holds on entry by the preheader initialisation. Between the increment of $i$ and the update of $s$ there is no other statement, and after both $s_{\text{old}} + c\,k = c\,i_{\text{old}} + d + c\,k = c(i_{\text{old}} + k) + d = c\,i_{\text{new}} + d$, so it holds again. Nothing else changes $i$ or $s$, so it holds throughout. The copy $j = s$ stands exactly where $j = c\,i + d$ stood, and at that point $s = c\,i + d$, so it assigns $j$ the value the original assigned. No other statement of either program assigns $j$, so $j$ agrees at every later point, after the loop included. The multiplication has become one addition per iteration. When the definition of $j$ sits right after the increment, $j$ and $s$ are equal from that point on, and copy propagation folds $s$ into $j$. When the only remaining use of $i$ is the loop test $i \le n$ and $c > 0$, the test can be rewritten as $s \le c\,n + d$ and $i$ removed.

(b) Since $y$ and $z$ do not change in the loop, computing $y \text{ op } z$ once before the loop gives the value every execution in the loop would give. Condition (1) ensures no other definition of $x$ is overwritten by the hoisted one; condition (2) ensures no use inside the loop expected an earlier value of $x$. Condition (3) handles paths that leave the loop without executing the statement: if the statement's block dominates the exit, every path to that exit runs it, so the hoisted value is the one the original would have left in $x$. Without (3), a path that skips the statement would see $x$'s old value originally but the hoisted value after the move. Placing the code in the header instead of a preheader would still execute it every iteration, which defeats the purpose.

The local rewrites need only the facts they name: constant folding evaluates an operator on constant operands; constant propagation replaces $x$ by $c$ where only the definition $x = c$ reaches; copy propagation replaces $x$ by $y$ where only `x = y` reaches and $y$ is unchanged since; dead-code elimination removes an assignment whose target is not live after it; strength reduction replaces $x \times 2^s$ by `x << s`.

**GATE use.** Questions ask which transformation was applied between two code versions, or what the code becomes after a stated sequence of optimizations. The traps are moving invariant code to the header instead of the preheader, hoisting an assignment that executes only on some paths, and forgetting the preheader initialisation of a strength-reduced variable.

**Check.** The loop `i = 0; do { j = 4 * i + 8; i = i + 1; print j } while (i < 5); print j` prints 8 12 16 20 24 and then 24. With $s = 8$ in the preheader, `s = s + 4` after `i = i + 1` and `j = s` in place of the multiply, it prints the same six values. Deleting the multiply and updating $j$ itself right after `i = i + 1` prints 12 16 20 24 28 and then 28, the trap the claim warns about. A randomised test over 1000 choices of $c$, $d$, $k$, $i_0$ and trip count, with $j$'s definition before and after the increment, finds no difference between the original and the $s$-version, and finds the direct update wrong in every run with the definition before the increment and $c\,k \ne 0$. Hoisting `x = y + z` (with $y = 3$, $z = 4$) out of `if (f) x = y + z` in a loop whose branch is never taken changes the final $x$ from 0 to 7, violating (3). An unconditional `x = 3 + 4` hoists safely when the loop runs at least once, but in a top-tested loop that runs zero times $x$ ends 7 instead of 0, which is why (3) asks for dominance of the exits, and the body does not dominate the exit from the header.

## Reaching definitions, available expressions and the iterative solver
<!-- topics: cd-sdt-ir-optimization.dataflow-framework -->

**Claim.** (a) Reaching definitions: with $\mathrm{GEN}[B]$ the definitions in $B$ that reach its end (the last definition of each variable in $B$) and $\mathrm{KILL}[B]$ the other definitions in the program of the variables $B$ defines,

$$\mathrm{OUT}[B] = \mathrm{GEN}[B] \cup (\mathrm{IN}[B] - \mathrm{KILL}[B]), \qquad \mathrm{IN}[B] = \bigcup_{P \in \mathrm{pred}(B)} \mathrm{OUT}[P].$$

(b) Available expressions: with $e\_\mathrm{gen}[B]$ the expressions computed in $B$ whose operands are not reassigned later in $B$ and $e\_\mathrm{kill}[B]$ the expressions with an operand assigned in $B$,

$$\mathrm{OUT}[B] = e\_\mathrm{gen}[B] \cup (\mathrm{IN}[B] - e\_\mathrm{kill}[B]), \qquad \mathrm{IN}[B] = \bigcap_{P \in \mathrm{pred}(B)} \mathrm{OUT}[P].$$

(c) Iterating the equations terminates. Reaching definitions starts from empty sets; available expressions starts with $\mathrm{OUT}[\mathrm{entry}] = \emptyset$ and every other OUT equal to the set $U$ of all expressions. Starting available expressions from empty sets gives a solution that is too small inside loops.

**Proof.** (a) A definition $d$ reaches the end of $B$ either because it is in $B$ and no later statement of $B$ redefines its variable (that is $\mathrm{GEN}[B]$), or because it reaches the start of $B$ and $B$ does not redefine its variable (that is $\mathrm{IN}[B] - \mathrm{KILL}[B]$). The definition "some path with no redefinition" is existential, so $d$ reaches the start of $B$ if it reaches the end of some predecessor: union.

(b) An expression $y + z$ is available at the end of $B$ if $B$ computes it with no later change of $y$ or $z$, or if it is available on entry and $B$ never assigns $y$ or $z$. A definition subtracts first and then adds, so an expression recomputed after its operand changes stays in $e\_\mathrm{gen}$. The definition quantifies over every path from the entry, so availability at the start of $B$ needs availability at the end of every predecessor: intersection.

(c) The sets live in a finite lattice (subsets of the definitions, or of $U$), and the transfer functions are monotone: a larger IN gives a larger OUT. Starting from empty sets, each round can only add elements to a union analysis; starting from $U$, each round can only remove elements from an intersection analysis. Each set changes at most $\lvert D \rvert$ or $\lvert U \rvert$ times, so iteration stops. The equations of a loop have more than one solution; union analyses want the smallest (nothing reaches unless a path proves it), intersection analyses want the largest (everything is available unless a path disproves it). Starting from empty sets on a must analysis lets the back edge contribute $\emptyset$ to an intersection, and the solution can stay empty for good.

**GATE use.** Questions ask for IN or OUT of a block for reaching definitions, which definitions reach a use, or whether an expression can be reused at a point. Pick the direction and meet first: reaching definitions forward with union, available expressions forward with intersection. The traps are keeping an earlier definition of the same variable in GEN, and initialising an intersection analysis to empty.

**Check.** With $B_1$: `d1 i = m - 1`, `d2 j = n`, `d3 a = u1`; $B_2$: `d4 i = i + 1`, `d5 j = j - 1`; $B_3$: `d6 a = u2`; $B_4$: `d7 i = u3`; and edges $B_1 B_2$, $B_2 B_3$, $B_2 B_4$, $B_3 B_4$, $B_4 B_2$, the solver gives $\mathrm{IN}[B_2] = \{d_1, d_2, d_3, d_5, d_6, d_7\}$, $\mathrm{OUT}[B_2] = \{d_3, d_4, d_5, d_6\}$, $\mathrm{OUT}[B_4] = \{d_3, d_5, d_6, d_7\}$, after 3 passes, the last one confirming. For available expressions with $B_1$ computing $a + b$, a loop header $B_2$ computing nothing, a body $B_3$ computing $c \times d$ with $B_3 \to B_2$, and an exit block $B_4$ after $B_2$, the universal start gives $\mathrm{IN}[B_2] = \{a + b\}$, so $B_4$ can reuse $a + b$; the empty start gives $\mathrm{IN}[B_2] = \emptyset$ and misses it.

## Liveness: the backward equations and register sharing
<!-- topics: cd-sdt-ir-optimization.liveness -->

**Claim.** With $\mathrm{USE}[B]$ the variables read in $B$ before any write to them in $B$, and $\mathrm{DEF}[B]$ the variables written in $B$ before any read of them in $B$,

$$\mathrm{IN}[B] = \mathrm{USE}[B] \cup (\mathrm{OUT}[B] - \mathrm{DEF}[B]), \qquad \mathrm{OUT}[B] = \bigcup_{S \in \mathrm{succ}(B)} \mathrm{IN}[S],$$

with $\mathrm{OUT}$ of the exit block empty unless something is live after the procedure. Iterating from empty sets, preferably in reverse block order, reaches the least solution, which is the set of live variables. An assignment to a variable that is dead right after it is dead code, and two variables never live at the same point can share a register.

**Proof.** Variable $x$ is live at a point when some path from that point reads $x$ before writing it. Take a path from the start of $B$. Either its first access to $x$ inside $B$ is a read, so $x$ is live at entry whatever happens later: that is $x \in \mathrm{USE}[B]$. Or its first access in $B$ is a write, so $x$ is dead at entry on this path: $x \in \mathrm{DEF}[B]$. Or $B$ does not touch $x$, and $x$ is live at entry exactly when it is live at the exit: $x \in \mathrm{OUT}[B] - \mathrm{DEF}[B]$. The cases are exclusive because the first access is unique, which gives the IN equation; a statement `x = x + 1` reads before it writes, so $x \in \mathrm{USE}$ and $x \notin \mathrm{DEF}$. Liveness asks for some path, and a path from the exit of $B$ continues into some successor, so OUT is the union over successors. Information flows from uses back toward definitions, so the analysis runs backward. The sets only grow from empty and are bounded by the set of variables, so iteration terminates; the least fixpoint is right because a variable is live only when a real path shows it.

**GATE use.** The 2-mark MSQ asks which variables are live at the entry or exit of a block, or for the minimum number of registers. Compute USE and DEF per block, iterate backward, and repeat until nothing changes. The trap is stopping after one pass when a back edge carries a use at the loop head into the end of the body, and confusing DEF with "assigned anywhere in the block".

**Check.** $B_1$: `a = 0`; $B_2$: `b = a + 1`, `c = c + b`, `a = b * 2`; $B_3$: `if a < N goto B2`; $B_4$: `return c`; edges $B_1 B_2$, $B_2 B_3$, $B_3 B_2$, $B_3 B_4$. Then $\mathrm{USE}[B_2] = \{a, c\}$ and $\mathrm{DEF}[B_2] = \{b\}$, since $a$ is read before it is written. The solver gives $\mathrm{IN}[B_1] = \{c\}$, $\mathrm{IN}[B_2] = \mathrm{IN}[B_3] = \{a, c\}$, $\mathrm{IN}[B_4] = \{c\}$ in 2 passes. Per statement, $a$ is dead between `b = a + 1` and `a = b * 2`, exactly where $b$ is live, so the only interferences are $a$–$c$ and $b$–$c$: $a$ and $b$ share one register, 2 registers in all.

## Constant propagation: the lattice and why it is not distributive
<!-- topics: cd-sdt-ir-optimization.constant-propagation -->

**Claim.** Each variable takes a value in the lattice with UNDEF on top, the constants in the middle and NAC at the bottom, with meet

$$\mathrm{UNDEF} \wedge v = v, \quad c \wedge c = c, \quad c_1 \wedge c_2 = \mathrm{NAC}\ (c_1 \ne c_2), \quad \mathrm{NAC} \wedge v = \mathrm{NAC}.$$

The analysis runs forward. The transfer for `x = y op z` gives $x$ the folded constant when $y$ and $z$ are constants, NAC when either is NAC, and UNDEF otherwise. The meet is commutative, associative and idempotent, the transfer functions are monotone, so iteration terminates; but the framework is not distributive: $f(m_1 \wedge m_2)$ can be strictly lower than $f(m_1) \wedge f(m_2)$, so the iterative solution can lose constants that hold on every path. Requiring the same constant on every incoming path makes it a must-style analysis.

**Proof.** The meet is the greatest lower bound in a lattice of height 3, so it is commutative, associative and idempotent. Monotonicity of `+`: lowering an operand moves it from UNDEF to a constant or from a constant to NAC, and each such step moves the result down or leaves it, never up. Every variable can move down at most twice, so iteration from UNDEF stops after finitely many changes. For the failure of distributivity, take the paths $m_1 = \{x = 2, y = 3\}$ and $m_2 = \{x = 3, y = 2\}$ meeting before `z = x + y`. Separately, $f(m_1)$ and $f(m_2)$ both give $z = 5$, so their meet is $z = 5$. At the join, $x = 2 \wedge 3 = \mathrm{NAC}$ and $y = \mathrm{NAC}$, so $f(m_1 \wedge m_2)$ gives $z = \mathrm{NAC}$. The analysis meets before applying the transfer, so it reports NAC although $z$ is 5 on every path. Monotonicity still gives $f(m_1 \wedge m_2) \le f(m_1) \wedge f(m_2)$, so the answer is safe, only imprecise.

**GATE use.** Questions ask which variables are constant after a join, the folded value of an expression, or whether the analysis is may or must and distributive. The traps are calling it a may analysis, treating a variable constant on one path as constant after the join, and expecting the analysis to find $z = 5$ in the swapped-values example.

**Check.** Exhaustive tests over UNDEF, NAC and the constants 1, 2, 3 confirm the meet laws, monotonicity of `+`, the inequality $f(m_1 \wedge m_2) \le f(m_1) \wedge f(m_2)$ in every case, and at least one case where equality fails. The swapped example gives $z = 5$ on each path and NAC after the meet. With $x = 3$ on both arms and $y = 5$ on one and $7$ on the other, after the join $x = 3$, $y = \mathrm{NAC}$, $x + y = \mathrm{NAC}$, and $x \times 2$ folds to 6.
