# Instruction pipelining: derivations

## The space-time diagram and the $k + n - 1$ cycle count
<!-- topics: coa-pipelining.pipeline-basics, coa-pipelining.speedup-throughput -->

**Claim.** A $k$-stage pipeline accepts one new instruction per cycle, every stage takes exactly one cycle, and nothing stalls. Number the instructions $1, \dots, n$ and the stages $1, \dots, k$ (for the classic pipeline IF = 1, ID = 2, EX = 3, MEM = 4, WB = 5). Then instruction $i$ is in stage $j$ during cycle $i + j - 1$, and the last instruction leaves the last stage at the end of cycle

$$C(n, k) = k + n - 1 .$$

Each instruction still takes $k$ cycles from IF to WB, so pipelining leaves the latency of one instruction unchanged (it lengthens it, once latches are counted) and raises throughput.

**Derivation.** Induction on $i$. Instruction 1 enters stage 1 in cycle 1 and moves one stage per cycle, so it is in stage $j$ in cycle $j$. Suppose instruction $i - 1$ is in stage $j$ in cycle $i + j - 2$. Instruction $i$ is fetched in the cycle after instruction $i - 1$ is fetched, which is cycle $i$, and since it moves one stage per cycle it reaches stage $j$ in cycle $i + j - 1$. Stage $j$ then holds instruction $i$ in cycle $i + j - 1$ and instruction $i - 1$ in cycle $i + j - 2$, so no two instructions ever occupy one stage in one cycle; the pipeline registers between stages are what let each stage hold its own instruction's partial results. The last instruction, $i = n$, is in stage $k$ in cycle $n + k - 1$. Read another way: the first instruction needs $k$ cycles to fill the pipeline, and each of the other $n - 1$ instructions completes one cycle after the one before it, giving $k + (n - 1)$.

**GATE use.** Every timing NAT starts from this count. The traps are $nk$ (no overlap at all) and $n + k$ (one cycle too many). With stalls, add the stall cycles to $k + n - 1$; a later section shows why the stalls must be counted on the actual timeline rather than summed pair by pair.

**Check.** For $k = 5$ and $n = 4$: $5 + 4 - 1 = 8$ cycles, with instruction 4 in IF in cycle 4 and in WB in cycle 8. A cycle-level simulator of the 5-stage pipeline gave $n + 4$ cycles for $n = 1, \dots, 29$ independent instructions, and placed instruction $i$ in IF in cycle $i$ and in WB in cycle $i + 4$.

## The clock cycle is the slowest stage plus the latch delay
<!-- topics: coa-pipelining.cycle-time -->

**Claim.** Let stage $i$ have logic delay $\tau_i$ and let each pipeline register add $d$ (setup time plus clock-to-output). All stages share one clock. Then the shortest workable clock period is

$$\tau = \max_{1 \le i \le k} \tau_i + d .$$

If the slowest stage is split, or work is moved between stages, the new period is the new maximum plus $d$, and for long instruction streams the throughput improves by the factor $\tau_{\text{old}}/\tau_{\text{new}}$. For a fixed amount of logic $T$ cut into $k$ equal stages, $\tau = T/k + d$, so the speedup over the unpipelined datapath is $T/(T/k + d)$, which stays below $T/d$ however deep the pipeline is.

**Derivation.** In each cycle, stage $i$ takes its inputs from the register in front of it, needs $\tau_i$ for its logic to settle, and its result must reach the next register in time to be captured, which costs $d$. So the period must satisfy $\tau \ge \tau_i + d$ for every $i$ at once, that is $\tau \ge \max_i \tau_i + d$; and that value is enough, because then every stage meets its own constraint. The faster stages finish early and sit idle for $\tau - d - \tau_i$ in every cycle, which is the cost of unbalanced stages. Splitting stage $j$ replaces $\tau_j$ by its parts, each with its own register, so the maximum can only fall or stay, and the latch delay is paid once per cycle in both designs. For large $n$ the throughput is $1/\tau$ (the section after next), hence the ratio $\tau_{\text{old}}/\tau_{\text{new}}$. With $T$ split evenly into $k$ stages each stage has delay $T/k$, so $\tau = T/k + d$; the unpipelined instruction takes $T$, and $T/(T/k + d) < T/d$ because $T/k > 0$.

**GATE use.** The 1-mark cycle-time MCQ is a single maximum plus the latch; the distractors are the forgotten latch, the sum of the delays, and a latch added to every stage. Stage-splitting MCQs ask for the throughput gain: recompute the maximum over the new stage list and add the latch to both periods, which makes the gain smaller than the ratio of the raw maxima.

**Check.** Stages 200, 150, 250, 200 and 150 ps with $d = 50$ ps give $\tau = 300$ ps. Stages 5, 7, 10, 8 and 6 ns with $d = 1$ ns give 11 ns; splitting the 10 ns stage into two 5 ns stages gives the list 5, 7, 5, 5, 8, 6, a new maximum of 8 and a period of 9 ns, so the gain is $11/9 \approx 1.22$, against $10/8 = 1.25$ if the latch is ignored. With $T = 10$ ns and $d = 0.5$ ns: $k = 5$ gives $\tau = 2.5$ ns and speedup 4; $k = 10$ gives 1.5 ns and 6.67; $k = 20$ gives 1 ns and 10; $k = 1000$ gives 0.51 ns and 19.6, approaching the bound $T/d = 20$.

## Speedup, efficiency and throughput
<!-- topics: coa-pipelining.speedup-throughput -->

**Claim.** Take $n$ instructions, no stalls, the pipelined period $\tau = \max_i \tau_i + d$, and a non-pipelined machine that takes $\sum_i \tau_i$ per instruction with no latches. Then

$$S = \frac{T_{\text{non-pipe}}}{T_{\text{pipe}}} = \frac{n \sum_{i} \tau_i}{(k + n - 1)\,\tau} \xrightarrow{\,n \to \infty\,} \frac{\sum_i \tau_i}{\tau} \le k, \qquad \eta = \frac{S}{k}, \qquad \text{Throughput} = \frac{n}{(k + n - 1)\,\tau} \xrightarrow{\,n \to \infty\,} \frac{1}{\tau}.$$

The limit equals $k$ exactly when the stages are equal and $d = 0$. In that ideal case $S = \frac{nk}{k + n - 1}$ and $\eta = \frac{n}{k + n - 1}$, which is at least $1 - \epsilon$ once $n \ge \frac{(1 - \epsilon)(k - 1)}{\epsilon}$.

**Derivation.** The pipelined time is $k + n - 1$ cycles of length $\tau$ (first section). The non-pipelined machine runs the instructions one after another, each through all the logic, so it takes $n \sum_i \tau_i$; writing this as $nk\tau$ is right only when every stage takes $\tau$ and there is no latch. Dividing gives $S$, and as $n \to \infty$ the factor $n/(k + n - 1) \to 1$, leaving $\sum_i \tau_i/\tau$. Since every $\tau_i \le \max_i \tau_i \le \tau$, the sum is at most $k\tau$, so the limit is at most $k$; equality needs every $\tau_i = \tau$, that is equal stages and $d = 0$. With equal stages and $d = 0$, $\sum_i \tau_i = k\tau$ and $S = nk/(k + n - 1)$, so $\eta = S/k = n/(k + n - 1)$. Solving $n/(k + n - 1) \ge 1 - \epsilon$ gives $n\epsilon \ge (1 - \epsilon)(k - 1)$. Throughput is instructions completed per unit time, $n$ over the pipelined time; for large $n$ it tends to one instruction per cycle.

**GATE use.** The 2-mark NAT gives stage delays and a latch and asks for the speedup for $n$ instructions. The traps are $nk\tau$ for the non-pipelined time with unequal stages, putting the latch into the non-pipelined time when the question does not, and quoting the ideal $k$ when $n$ is small or the stages are unbalanced. Efficiency is $S/k$, not $S$ divided by the number of instructions.

**Check.** Stages 200, 150, 250, 200, 150 ps, $d = 50$ ps, $n = 100$: $T_{\text{pipe}} = 104 \times 300 = 31200$ ps, $T_{\text{non-pipe}} = 100 \times 950 = 95000$ ps, $S \approx 3.045$, $\eta \approx 60.9\%$, throughput $100/31200$ per ps $\approx 3.21 \times 10^9$ instructions per second against the limit $1/\tau \approx 3.33 \times 10^9$; the large-$n$ speedup is $950/300 \approx 3.17$. A 4-stage pipeline with a 4 ns clock against 16 ns per instruction, $n = 1000$: $16000/4012 \approx 3.99$. For $k = 5$ ideal stages, $\eta = 0.9$ needs $n \ge 9 \cdot 4 = 36$: $36/40 = 0.9$ while $35/39 < 0.9$.

## Effective CPI, execution time, MIPS and speedup with stalls
<!-- topics: coa-pipelining.cpi-performance, coa-pipelining.control-hazards -->

**Claim.** Let a stream of $\mathrm{IC}$ instructions run on a pipeline that issues one instruction per cycle when nothing stalls. Split the stall causes into classes $j$: a fraction $f_j$ of the instructions belongs to class $j$, a fraction $p_j$ of those actually stalls, and each such stall costs $s_j$ cycles. If no two stalls overlap in time, then for large $\mathrm{IC}$

$$\mathrm{CPI} = 1 + \sum_j f_j\, p_j\, s_j, \qquad T = \mathrm{IC} \times \mathrm{CPI} \times \tau, \qquad \mathrm{MIPS} = \frac{f}{\mathrm{CPI} \times 10^{6}}, \qquad \mathrm{IPC} = \frac{1}{\mathrm{CPI}},$$

where $f = 1/\tau$ is the clock frequency in Hz. The speedup over a non-pipelined machine that takes $T_{\text{inst}}$ per instruction is $T_{\text{inst}}/(\mathrm{CPI} \times \tau)$, which is $k/\mathrm{CPI}$ when the stages are equal and $d = 0$.

**Derivation.** CPI is defined as total cycles divided by instruction count. Without stalls the stream takes $\mathrm{IC} + k - 1$ cycles. Every stall cycle delays the completion of the last instruction by one cycle, provided it does not coincide with another stall (a stalled instruction holds everything behind it, and a bubble, once inserted, travels to the end of the pipeline). The number of stall cycles from class $j$ is the count of its instructions, $f_j \mathrm{IC}$, times the fraction that stall, times the cycles each, so the total is $\mathrm{IC} \sum_j f_j p_j s_j$. Dividing $\mathrm{IC} + k - 1 + \mathrm{IC}\sum_j f_j p_j s_j$ by $\mathrm{IC}$ and letting $\mathrm{IC}$ grow removes the fill term $(k - 1)/\mathrm{IC}$ and gives the CPI formula. If two stalls do overlap, one wait hides part of the other and the formula overstates the CPI. Time is cycles times the period, $\mathrm{IC} \cdot \mathrm{CPI} \cdot \tau$. MIPS is millions of instructions per second: $\mathrm{IC}/(T \cdot 10^6) = 1/(\mathrm{CPI} \cdot \tau \cdot 10^6) = f/(\mathrm{CPI} \cdot 10^6)$. Dividing the non-pipelined time $\mathrm{IC} \cdot T_{\text{inst}}$ by $T$ gives the speedup, and $T_{\text{inst}} = k\tau$ in the ideal case turns it into $k/\mathrm{CPI}$.

**GATE use.** The 2-mark NAT lists branch and load statistics: multiply frequency, fraction that stalls and penalty for each source, then add 1. The trap is charging the branch penalty on every branch when only taken or mispredicted branches pay it (the branch section derives which ones do). A second trap is comparing two machines by CPI alone when their clocks differ; compare $\mathrm{CPI} \times \tau$.

**Check.** Branches 20% of instructions, 60% of them taken, 2 cycles per taken branch under predict-not-taken; loads 25%, 40% of them followed at once by a use, 1 cycle each: $\mathrm{CPI} = 1 + 0.24 + 0.10 = 1.34$. With $\tau = 300$ ps that is $1/(1.34 \times 300 \times 10^{-12} \times 10^6) \approx 2488$ MIPS, $10^6$ instructions take $402\ \mu$s, and the speedup over a 950 ps unpipelined instruction is $950/(1.34 \times 300) \approx 2.36$. Freezing on every branch instead costs $0.20 \times 1 \times 2 = 0.40$ for branches, CPI 1.50; resolving in ID under predict-not-taken costs $0.20 \times 0.6 \times 1 = 0.12$, CPI 1.22.

## Structural hazards: one memory port and the split-cycle register file
<!-- topics: coa-pipelining.structural-hazards -->

**Claim.** In the stall-free 5-stage timing, instruction $i$ is in MEM in cycle $i + 3$, the cycle in which instruction $i + 3$ is in IF. With one memory port shared by IF and MEM, and the port given to MEM, every load or store whose MEM cycle falls while instructions remain to be fetched delays the fetch stream by one cycle. For a long stream with a fraction $f_{\text{mem}}$ of loads and stores and no other hazards, $\mathrm{CPI} \to 1 + f_{\text{mem}}$. Separate instruction and data memories (split I and D caches) remove the conflict. The register file has no such conflict when it is written in the first half of the cycle and read in the second half, which also lets an instruction in ID read a value written in WB in the same cycle.

**Derivation.** By the first section, stage $j$ of instruction $i$ is in cycle $i + j - 1$; MEM is $j = 4$ and IF is $j = 1$, so instruction $i$'s MEM cycle is $i + 3$, which is instruction $(i + 3)$'s IF cycle. A memory instruction in MEM needs the single port in that cycle, so no fetch can happen; the instruction that would have been fetched is fetched one cycle later and every later instruction moves back one cycle with it. Instructions already in the pipeline keep their timing, so each later memory access again takes exactly one fetch cycle. Every cycle while fetching continues is therefore either a fetch cycle or a data-access cycle, so the cycles up to the last fetch number $n$ plus the data accesses made in that time, and dividing by $n$ gives $1 + f_{\text{mem}}$ for long streams; the few accesses made after the last fetch cost nothing. Split caches give each stage its own port, so the cycle is never contested. For the register file, WB and ID touch it in the same cycle (instruction $i$ in WB is in cycle $i + 4$, the ID cycle of instruction $i + 3$). Writing in the first half and reading in the second half separates the two uses in time, and the reader sees the new value.

**GATE use.** MCQs ask which stages conflict on a single memory (IF and MEM) and what fixes it (split I and D caches, or a dual-ported memory). A CPI question may add $f_{\text{mem}} \times 1$ to the stall sum. The split-cycle register file is the convention behind the "2 stalls for an adjacent RAW without forwarding" rule; without it the count rises by one.

**Check.** A load followed by four ALU instructions on a single-ported memory: the simulator fetched the instructions in cycles 1, 2, 3, 5 and 6, skipping cycle 4 for the load's MEM, and finished in 10 cycles instead of 9. On random streams of 20,000 instructions with 25% and 40% loads, the measured CPI was 1.249 and 1.400 against $1 + f_{\text{mem}}$ of 1.249 and 1.400 for the sampled fractions.

## RAW, WAR and WAW, and why an in-order 5-stage pipeline stalls only on RAW
<!-- topics: coa-pipelining.data-hazard-types, coa-pipelining.out-of-order -->

**Claim.** For instructions $I$ before $J$ in program order, with destination sets $D(\cdot)$ and source sets $R(\cdot)$: RAW (true dependence) means $D(I) \cap R(J) \ne \emptyset$, WAR (anti-dependence) means $R(I) \cap D(J) \ne \emptyset$, and WAW (output dependence) means $D(I) \cap D(J) \ne \emptyset$. In a pipeline where every instruction reads its registers in ID, writes in WB, passes through the stages in program order and spends the same number of cycles between ID and WB, WAR and WAW can never produce a wrong value; only RAW needs stalls or forwarding. Register renaming removes every WAR and WAW dependence and keeps every RAW dependence.

**Proof.** Let instruction $i$ read in cycle $D_i$ and write in cycle $W_i = D_i + c$ for a fixed $c > 0$ ($c = 3$ for the classic pipeline). In-order flow gives $D_i < D_j$ whenever $i < j$, hence $W_i < W_j$. WAR: $I$ reads at $D_I$, $J$ writes at $W_J = D_J + c > D_I$, so $I$ always reads before $J$ overwrites, and sees the old value it should. WAW: $W_I < W_J$, so $J$'s value is written last and survives, as program order requires. RAW: $J$ reads at $D_J$ and $I$ writes at $W_I = D_I + c$; for adjacent instructions $D_J = D_I + 1 < D_I + c$, so the read would come first and get a stale value. That is the only case the hardware must handle. WAR and WAW become real hazards when a later instruction can write before an earlier one reads or writes, which happens with out-of-order execution or with functional units of different latencies that complete out of order.

Renaming gives each instruction's destination a fresh physical register and rewrites each later source to the newest physical name of its architectural register. After renaming no two instructions share a destination, so WAW is impossible, and a later instruction never writes a register that an earlier one reads, since its destination is new, so WAR is impossible. A source still names the physical register written by its producer, so every RAW edge survives: it is the data flow of the program, and no naming scheme changes what value an instruction needs.

**GATE use.** MSQs list a short sequence and ask which dependences exist; check every ordered pair three ways. The trap is reading the operand list backwards: in ADD R1, R2, R3 the destination is R1. Other MSQs test the facts above: in-order pipelines stall only on RAW, renaming removes WAR and WAW but never RAW, and forwarding shortens RAW stalls without removing the dependence.

**Check.** I1: ADD R1, R2, R3; I2: SUB R2, R4, R5; I3: MUL R1, R6, R2. A script that tests every ordered pair found WAR from I1 to I2 on R2, WAW from I1 to I3 on R1 and RAW from I2 to I3 on R2, and no RAW on R1, because I3 does not read R1. After renaming the destinations to P0, P1 and P2, I3 became MUL P2, R6, P1, and the only dependence left was RAW from I2 to I3 on P1.

## RAW stalls at distance $d$, forwarding, and the load-use stall
<!-- topics: coa-pipelining.forwarding-load-use, coa-pipelining.stall-counting -->

**Claim.** On the 5-stage pipeline, let a consumer be $d \ge 1$ instructions after its producer, with no other stall in between. A consumer reads its operands in ID or, with forwarding, needs them at the start of EX.

1. No forwarding, split-cycle register file: the consumer stalls $\max(0, 3 - d)$ cycles, so 2 for adjacent instructions and 1 at distance 2.
2. Full forwarding (EX/MEM and MEM/WB to the ALU inputs): an ALU producer costs 0 at every distance; a load costs $\max(0, 2 - d)$, so 1 cycle when the use immediately follows the load.

**Derivation.** Put the producer at position $p$ and the consumer at $p + d$; without stalls the producer is in EX in cycle $p + 2$, MEM in $p + 3$ and WB in $p + 4$, and the consumer is in ID in $p + d + 1$ and EX in $p + d + 2$. (1) Without forwarding the value exists only in the register file, written in the first half of cycle $p + 4$, and the split-cycle read lets ID read it in that same cycle. So the consumer's ID must be no earlier than $p + 4$, and it stalls $(p + 4) - (p + d + 1) = 3 - d$ cycles when that is positive. Without the split-cycle convention the read must come one cycle later and the count becomes $\max(0, 4 - d)$. (2) With forwarding the value is taken from a pipeline register as soon as it exists. An ALU result exists at the end of the producer's EX, cycle $p + 2$, so the consumer's EX must be no earlier than $p + 3$; it is in $p + d + 2 \ge p + 3$, so there is no stall. A loaded value exists only at the end of MEM, cycle $p + 3$, so the consumer's EX must be no earlier than $p + 4$, and it stalls $(p + 4) - (p + d + 2) = 2 - d$ cycles when that is positive. Forwarding cannot go back in time: the load-use pair needs the value at the start of the cycle in which the load is still reading memory, so one bubble remains. At $d = 1$ the value comes from the EX/MEM register (ALU) or MEM/WB (load after the bubble); at $d = 2$ from MEM/WB; at $d = 3$ the split-cycle register file supplies it. The compiler can remove the load-use bubble by placing an independent instruction between the load and its use, which makes $d = 2$.

**GATE use.** MCQs ask for the stalls of LW followed by a dependent ADD with forwarding (1) and without (2), and 2-mark NATs give a sequence and ask for the total cycles. The traps are charging the load-use bubble to an ALU-to-ALU pair, forgetting it on a load, and applying the without-forwarding count when the question grants forwarding.

**Check.** The cycle-level simulator placed one producer, $d - 1$ independent instructions and one consumer, and measured stalls over $k + n - 1$. ALU producer: 2, 1, 0, 0, 0 without forwarding and 0 at every distance with it, for $d = 1, \dots, 5$. Load producer: 2, 1, 0, 0, 0 without and 1, 0, 0, 0, 0 with forwarding. LW R1, 0(R2); ADD R3, R1, R4; SW R3, 0(R5) took 8 cycles with forwarding ($7 + 1$) and 11 without ($7 + 2 + 2$).

## Counting cycles for a sequence: the timing recurrence
<!-- topics: coa-pipelining.stall-counting, coa-pipelining.variable-latency -->

**Claim.** In an in-order 5-stage pipeline where an instruction waits in ID until it may proceed and every instruction behind it waits in its own stage, let $W_p$ be the WB cycle of instruction $p$ and let $P(i)$ be the producers of $i$'s source registers (the latest earlier writer of each).

1. Without forwarding, split-cycle register file, 1-cycle EX: the cycle $D_i$ in which instruction $i$ completes ID satisfies $D_1 = 2$ and $D_i = \max\big(D_{i-1} + 1,\ \max_{p \in P(i)} W_p\big)$, with $W_i = D_i + 3$.
2. With full forwarding and EX latencies $L_i$ on one non-pipelined EX unit: the first EX cycle $X_i$ and the last $E_i = X_i + L_i - 1$ satisfy $X_1 = 3$ and $X_i = \max\big(E_{i-1} + 1,\ E_p + 1 \text{ for ALU } p \in P(i),\ E_p + 2 \text{ for a load } p \in P(i)\big)$, with $W_i = E_i + 2$.

The total is $W_n$ cycles, and the stall count is $W_n - (k + n - 1)$. Stalls from different dependences do not add: an instruction stalls only by the part of its requirement that the stalls ahead of it have not already covered.

**Derivation.** (1) ID holds one instruction, so $i$ can complete ID no earlier than the cycle after $i - 1$ did; it must also wait until every producer has written in WB, which the split-cycle file lets it read in that same cycle. No other constraint binds: after ID the instruction moves one stage per cycle, and EX, MEM and WB are each free the cycle after $i - 1$ used them, since $i - 1$ was one cycle ahead. The fetch constraint $D_i \ge i + 1$ follows from $D_i \ge D_{i-1} + 1$ by induction. So $i$ leaves ID at the earliest permitted cycle, which is the maximum, and reaches WB 3 cycles later. (2) The EX unit is busy through $E_{i-1}$, so $X_i \ge E_{i-1} + 1$. An ALU result is forwarded from the end of $E_p$, so the consumer's EX may start at $E_p + 1$; a load's value appears at the end of its MEM, cycle $E_p + 1$, so the consumer's EX may start at $E_p + 2$. MEM and WB follow EX in single cycles and stay in order, because $E_i > E_{i-1}$. Each extra EX cycle of instruction $i$ raises $E_i$ by one and so delays everything behind it, unless a later instruction was waiting anyway. In both cases the stall-free timeline ends at $k + n - 1$, so the excess is the stall count. A dependence whose stall is already covered by an earlier stall adds nothing, which is why summing the pairwise counts of the previous section can overcount.

**GATE use.** The 2-mark "how many cycles" NAT. Fill the table one instruction at a time with the recurrence, then read the last WB cycle. The traps are summing pairwise stall counts (an instruction that depends on two earlier ones stalls by the larger requirement, not the sum), forgetting that a stalled instruction holds independent instructions behind it, and using $k + n - 1$ when EX latencies differ.

**Check.** Without forwarding, I1: ADD R1, R2, R3; I2: SUB R4, R1, R5; I3: AND R6, R1, R7; I4: OR R8, R4, R6 give $D = 2, 5, 6, 9$ (I2 waits for $W_1 = 5$; I3 needs $W_1 = 5$, already covered by $D_2 + 1 = 6$; I4 needs $W_3 = 9$) and $W_4 = 12$, so 12 cycles and 4 stalls, although the pairwise counts would add I3's 1 stall for its distance-2 use of R1. With forwarding and MUL taking 3 EX cycles, MUL R1, R2, R3; ADD R4, R1, R5; SUB R6, R7, R8; MUL R9, R4, R6 give $X = 3, 6, 7, 8$ and $E = 5, 6, 7, 10$, so $W_4 = 12$. The cycle-level simulator agreed on both sequences, and it matched the recurrences in 5,509 runs on random sequences of up to 8 ALU, load and multi-cycle instructions (recurrence 1 only where every EX takes one cycle).

## Branch penalty: stage of resolution and fetch policy
<!-- topics: coa-pipelining.control-hazards -->

**Claim.** A branch is fetched in cycle $c$ and resolves (outcome and target known) at the end of stage $r$, counting IF as stage 1, so in cycle $c + r - 1$; the correct next instruction can be fetched in cycle $c + r$. Then exactly $r - 1$ instructions are fetched before the outcome is known, and the branch costs $r - 1$ cycles whenever those fetches are not on the correct path. Per instruction,

$$\text{stalls}_{\text{branch}} = f_{\text{branch}} \times p_{\text{wrong}} \times (r - 1),$$

with $p_{\text{wrong}} = 1$ when fetch freezes on every branch, the fraction of taken branches under predict-not-taken, and the misprediction rate under a predictor that supplies the target in IF. Resolution in EX ($r = 3$) costs 2 cycles; in ID ($r = 2$), 1.

**Derivation.** Fetch continues every cycle, so the fetches in cycles $c + 1, \dots, c + r - 1$, which number $r - 1$, all happen before cycle $c + r - 1$ ends. If they followed the right path they are kept and nothing is lost. If they did not, they are flushed, and the first useful fetch after the branch is in cycle $c + r$ instead of $c + 1$: a delay of $r - 1$ cycles for every later instruction. Freezing fetch until resolution loses the same $r - 1$ cycles on every branch. Predict-not-taken fetches the fall-through path, which is right exactly when the branch is not taken. Predict-taken needs the target, which a plain pipeline also learns only in stage $r$, so it saves nothing without a branch target buffer; with one, the target is available in IF and only mispredictions pay. Multiplying the per-branch loss by the fraction of branches that pay it and by the branch frequency gives the stall term, which enters the CPI formula. A deeper pipeline has a shorter cycle but resolves branches in a later stage, so $r - 1$ grows and the stall term with it.

**GATE use.** MCQs ask how the penalty changes when resolution moves from EX to ID (2 to 1). NATs combine the penalty with branch statistics in the CPI. The traps are charging not-taken branches under predict-not-taken, using $r$ instead of $r - 1$, and comparing a deep and a shallow pipeline by CPI without the clock.

**Check.** A ten-instruction stream with one taken branch under predict-not-taken took $14 + (r - 1)$ cycles for $r = 2, 3, 4$ (15, 16 and 17), and 14 cycles when the branch was not taken; freezing cost $r - 1$ in both cases. Model a deep and a shallow design with branches 20% of instructions and half of them taken: 5 stages, $\tau = 2.5$ ns and penalty 2 give $\mathrm{CPI} = 1.2$ and 3.0 ns per instruction; 10 stages, $\tau = 1.5$ ns and penalty 5 give $\mathrm{CPI} = 1.5$ and 2.25 ns, so the deeper design has the worse CPI and still finishes sooner.

## Delayed branches: how many slots and what may fill them
<!-- topics: coa-pipelining.delayed-branch, coa-pipelining.control-hazards -->

**Claim.** If the branch resolves in stage $r$, defining the $r - 1$ instructions after the branch as delay slots, which always execute whatever the outcome, removes the branch penalty when every slot holds useful work. A 5-stage pipeline that resolves in ID needs one slot. An instruction $X$ that comes before the branch may move into the slot when the branch does not read any register $X$ writes and no instruction $X$ moves past reads or writes $X$'s destination or writes $X$'s sources (no RAW, WAR or WAW dependence between $X$ and anything it is reordered with). If a fraction $u$ of slots is filled usefully and the rest hold NOPs, the branch cost per instruction is $f_{\text{branch}} (1 - u)(r - 1)$ for one-cycle slots.

**Proof.** The $r - 1$ fetches after the branch happen before resolution (previous section). If the architecture says these instructions run on both paths, the fetches are always on the correct path, nothing is flushed, and the target is fetched in cycle $c + r$, right after the last slot; no cycle is lost. A NOP in a slot is fetched and does nothing, which costs exactly the cycle the flush would have cost. For the move: $X$ ran before the branch in the original program and runs exactly once, on both paths, after it, so the only change is the relative order of $X$ and the branch (and of $X$ and the instructions it moved past). The branch reads its condition registers; if $X$ wrote one of them, the branch would now see the old value, so this case is forbidden. If $X$ reads or writes nothing the branch and the instructions it moves past touch, every value computed is the same as before, so both paths see the same state as in the original program.

**GATE use.** MCQs show the code before a branch and ask which instruction can fill the slot: pick one that the branch condition does not depend on. The traps are choosing the instruction that computes the branch's register, and believing the hardware discards the slot instruction when the branch is taken.

**Check.** ADD R5, R6, R7; SUB R1, R1, R3; BEQ R1, R2, L: the branch reads R1 and R2; ADD writes R5 and neither of the others reads or writes R5, so ADD moves into the slot, while SUB writes R1 and must stay. With one slot, branches at 20% and 60% of slots filled, the branch cost is $0.2 \times 0.4 \times 1 = 0.08$ cycles per instruction, so $\mathrm{CPI} = 1.08$ against 1.2 with NOP in every slot.

## One-bit and two-bit predictors on loop branches
<!-- topics: coa-pipelining.branch-prediction -->

**Claim.** A loop of $m$ iterations has a branch at the bottom whose outcomes are $m - 1$ taken (T) followed by one not-taken (N); run the loop $L$ times in a row.

1. A 1-bit predictor (predict the last outcome), with $m \ge 2$, mispredicts twice per loop execution after the first: at the exit, and at the first T of the next execution. From an initial N it makes $2L$ mispredictions; from an initial T, $2L - 1$.
2. A 2-bit saturating counter (states 0 to 3, predict T in states 2 and 3, move one step towards each outcome) that starts in state 2 or 3, with $m \ge 2$, mispredicts once per execution, at the exit: $L$ in all. From state 0 and $m \ge 4$ it makes $L + 2$.
3. From a strong state (0 or 3) a 2-bit counter needs two consecutive opposite outcomes to change its prediction; from a weak state (1 or 2) one is enough.

**Proof.** (1) The predictor holds the last outcome. At the exit it holds T, from the previous outcome, and the outcome is N: a miss. It now holds N, so the first outcome of the next execution, T, is a miss; the remaining $m - 2$ T outcomes follow a T and hit. So each execution after the first has 2 misses. The first execution has the exit miss plus a miss at its first T if the initial state is N: $2 + 2(L - 1) = 2L$, or $1 + 2(L - 1) = 2L - 1$ from T. (3) Prediction T means state $\ge 2$. From state 3 an N moves to 2, which still predicts T, and a second N moves to 1, which predicts N; from state 2 one N gives 1. The states 0 and 1 are symmetric. (2) Suppose an execution starts in state 2 or 3. Its first T hits and moves the counter to 3 or keeps it there, the other T outcomes hit and leave it at 3, and the exit N misses and moves it to 2. The next execution again starts in state 2, so every execution costs exactly one miss, and $m \ge 2$ guarantees the T that lifts state 2 back to 3 before the exit. From state 0, the first two T outcomes miss (0 to 1, then 1 to 2), the third T hits and lifts the counter to 3 (this needs $m - 1 \ge 3$), and the exit misses: 3 misses, then one per execution, $L + 2$ in all.

**GATE use.** NATs give a loop count, a predictor and an initial state, and ask for the mispredictions or the accuracy. Trace the state outcome by outcome. The traps are moving a 2-bit counter from strongly taken straight to predicting N on one miss, applying "two misses to flip" from a weak state, and forgetting the re-entry miss of a 1-bit predictor. BTFN predicts backward branches taken, which is what makes loop branches cheap for a static scheme.

**Check.** Loop T, T, T, N run 3 times from state 0: the counter goes 0, 1, 2, 3, 2 (misses at the first two T and at N), then hits all three T and misses each N: 5 mispredictions, while a 1-bit predictor from N makes 6. For $m = 10$ and $L = 10$, the 1-bit predictor from N misses 20 times (80% accuracy) and the 2-bit counter from 0 misses 12 times (88%). With $m = 3$ from state 0 the counter misses 3, 5, 6, 7 and 8 times for $L = 1, \dots, 5$, because the first execution ends in state 1, which is why the $L + 2$ formula needs $m \ge 4$. On an alternating T, N pattern of length 10, the 1-bit predictor from N missed all 10 (from T it misses 9) and the 2-bit counter 5, from state 0 or state 2. A script confirmed $2L$, $2L - 1$, $L$ and $L + 2$ for every $m$ from 2 (or 4) to 9 and $L$ from 1 to 6.
