# File systems: derivations

## Blocks, block addresses and the largest disk they can name
<!-- topics: os-file-systems.disk-capacity-arithmetic -->

**Claim.** A disk of $C$ bytes cut into blocks of $B$ bytes, with $B$ dividing $C$, has $n = C/B$ blocks. Giving every block a distinct address needs at least

$$a = \lceil \log_2 n \rceil$$

bits, and $a$-bit block addresses can name at most $2^a$ blocks, so they reach at most $D_{\max} = 2^a \times B$ bytes of disk. When $C = 2^c$ and $B = 2^b$, $n = 2^{c-b}$ and $a = c - b$; a byte address then needs $c$ bits, $c - b$ for the block and $b$ for the offset inside it. If one address value is reserved, for instance as a null pointer, the count to cover is $n + 1$.

**Derivation.** An $a$-bit string is a sequence of $a$ binary choices, so there are $2^a$ of them. Distinct blocks need distinct addresses, so the numbering is an injection from $n$ blocks into $2^a$ strings, which exists exactly when $n \le 2^a$ (the pigeonhole principle). Because $a$ is an integer, $n \le 2^a$ holds exactly when $a \ge \lceil \log_2 n \rceil$. In the other direction, $2^a$ addresses name $2^a$ blocks of $B$ bytes each, which is $D_{\max}$. Writing a byte's position as a block number and an offset is the division $x = iB + r$ with $0 \le r \le B - 1$, so for powers of two the $c$ bits of a byte address split into $c - b$ block bits and $b$ offset bits. Stored pointers take a whole number of bytes, so a file system that needs 27 bits still stores 4-byte pointers; the pointer size $p$ in the later sections is that stored size.

**GATE use.** MCQs ask for the minimum width of a block address or the largest disk a pointer width can serve; both come from writing $n$ as a power of two. The traps are the decimal gigabyte ($10^9$ in place of $2^{30}$), answering with the byte-address width $c$ or the offset width $b$ instead of $c - b$, and forgetting the ceiling when $n$ is not a power of two.

**Check.** A 1 TB disk with 4 KB blocks has $2^{40}/2^{12} = 2^{28}$ blocks and needs 28-bit addresses. 512 GB with 4 KB blocks has $2^{27}$ blocks, so 27 bits, while 39 bits would address bytes and 12 bits is the offset. 32-bit addresses with 4 KB blocks reach $2^{32} \times 2^{12} = 2^{44}$ bytes = 16 TB, and 1 GB of 4 KB blocks is $2^{18}$ blocks. A 100 GB disk ($100 \times 2^{30}$ bytes) with 4 KB blocks has 26,214,400 blocks, between $2^{24} = 16{,}777{,}216$ and $2^{25}$, so it needs 25 bits; read as $100 \times 10^9$ bytes it has 24,414,062 whole blocks and still needs 25. $2^{16}$ blocks with a reserved null value need 17 bits. A script confirmed $\lceil \log_2 n \rceil$ against the smallest $a$ with $2^a \ge n$ for every $n$ below 5,000.

## Disk geometry: capacity, rotational latency and transfer time
<!-- topics: os-file-systems.disk-capacity-arithmetic -->

**Claim.** A disk with $h$ recording surfaces, $t$ tracks per surface, $s$ sectors per track and $b$ bytes per sector, with the same number of sectors on every track, holds

$$C = h \times t \times s \times b$$

bytes. The address (cylinder $c$, head $x$, sector $y$), with $0 \le c \le t - 1$, $0 \le x \le h - 1$ and $0 \le y \le s - 1$, corresponds one-to-one to the linear sector number $L = (c \cdot h + x) \cdot s + y$. If the disk turns at $R$ revolutions per minute, one revolution takes $T_{\text{rot}} = 60/R$ seconds, the average rotational latency is $T_{\text{rot}}/2$, one sector passes under the head in $T_{\text{rot}}/s$, $k$ consecutive sectors of a track take $(k/s)\,T_{\text{rot}}$, and the sustained rate from one track is $s \cdot b / T_{\text{rot}}$ bytes per second. Reading one block takes $T_{\text{seek}} + T_{\text{rot}}/2 + T_{\text{transfer}}$ on average.

**Derivation.** A byte is fixed by choosing a surface, a track on it, a sector on that track and a byte in that sector, and different choices give different bytes, so the product rule gives $C$. The tracks at the same position on all surfaces form a cylinder, so the disk has $t$ cylinders of $h$ tracks each. For the linear number, the division algorithm recovers $y = L \bmod s$, $x = \lfloor L/s \rfloor \bmod h$ and $c = \lfloor L/(hs) \rfloor$, so different addresses give different values of $L$; there are $ths$ addresses and $ths$ values $0, \dots, ths - 1$, so the map is a bijection. (Sector numbers in CHS addresses conventionally start at 1, so subtract 1 first.) The platter turns at constant speed, so one sector, $1/s$ of the track, passes in $T_{\text{rot}}/s$, and $k$ sectors in $(k/s)T_{\text{rot}}$; one revolution delivers $s \cdot b$ bytes. When the target's angle relative to the head is uniform over a revolution, the wait for it is uniform on $[0, T_{\text{rot}})$, with mean $T_{\text{rot}}/2$. Seek, rotation and transfer happen one after another, so their times add, and so do their means.

**GATE use.** Questions give the geometry and ask for the capacity, the bits in a sector address, the data rate or the time to read some sectors. The traps are counting platters as surfaces (a platter usually has two), taking a full revolution as the average latency, and converting RPM wrongly; zoned disks put more sectors on outer tracks, which the formula ignores unless the question gives the counts.

**Check.** 16 surfaces, 1024 tracks per surface and 64 sectors of 512 B give $2^4 \times 2^{10} \times 2^6 \times 2^9 = 2^{29}$ B = 512 MB, and a sector address needs $4 + 10 + 6 = 20$ bits. At 7200 RPM, $T_{\text{rot}} \approx 8.333$ ms and the average latency is $\approx 4.167$ ms; a simulation of $10^6$ uniform angles averaged 4.17 ms. One sector takes $8.333/64 \approx 0.130$ ms, a 4 KB block of 8 sectors takes $\approx 1.042$ ms, and the track delivers $64 \times 512$ B per revolution, which is 3,932,160 B/s or 3.75 MB/s. With a 5 ms average seek, reading one 4 KB block takes $5 + 4.167 + 1.042 \approx 10.208$ ms. A script checked the linear numbering on a geometry of 3 surfaces, 5 tracks and 7 sectors: the 105 addresses map to distinct numbers from 0 to 104 and back.

## Index blocks: pointers per block and the reach of a k-level pointer
<!-- topics: os-file-systems.indexed-allocation, os-file-systems.unix-inode -->

**Claim.** A block of $B$ bytes holds

$$N = \frac{B}{p}$$

pointers of $p$ bytes each (rounded down if $p$ does not divide $B$). A file described by one index block can therefore have at most $N$ data blocks, so

$$S_{\max} = \frac{B}{p} \times B .$$

Call a pointer to a data block a 0-level pointer, and a pointer to an index block full of $(k-1)$-level pointers a $k$-level pointer. A $k$-level pointer reaches exactly $N^k$ data blocks, all different, through $1 + N + \dots + N^{k-1}$ index blocks when full. Its $j$-th data block, counting from 0, is found by writing $j$ in base $N$ with $k$ digits: the leading digit picks the entry in the top index block, the next digit the entry one level down, and so on.

**Proof.** The entries are laid side by side in the block, which gives the pointer count. For the reach, induct on $k$. A 0-level pointer reaches $1 = N^0$ data block through no index block. A $k$-level pointer names one index block whose $N$ entries are $(k-1)$-level pointers; by induction each reaches $N^{k-1}$ data blocks, and the sets are disjoint because every block in the tree has one parent, so the total is $N \cdot N^{k-1} = N^k$. The index blocks number one plus $N$ times those of a $(k-1)$-level pointer, which is $1 + N + \dots + N^{k-1}$. With the data blocks listed in order, top entry $d$ covers positions $dN^{k-1}$ to $(d+1)N^{k-1} - 1$, so $d = \lfloor j/N^{k-1} \rfloor$, the leading base-$N$ digit of $j$, and the remainder $j \bmod N^{k-1}$ is located the same way one level down. A single index block is the case $k = 1$: $N$ data blocks of $B$ bytes each. Galvin's linked scheme chains index blocks and keeps the last entry of each for the address of the next, so $m$ linked index blocks address $m(N - 1)$ data blocks.

**GATE use.** Every inode question starts with $N$. The traps are dividing by the pointer size in bits (4096/32 = 128 instead of 1024 for 4 KB blocks and 32-bit pointers) and counting the index blocks themselves as file data.

**Check.** 4 KB blocks with 4-byte pointers give $N = 1024$ and a single-index limit of $1024 \times 4$ KB = 4 MB; 512-byte blocks with 8-byte pointers give $N = 64$ and 32 KB; 1 KB blocks with 4-byte pointers give $N = 256$. A full triple-indirect tree with $N = 1024$ uses $1 + 1024 + 1024^2 = 1{,}049{,}601$ index blocks. With linked index blocks, a 1 GB file of $2^{18}$ blocks of 4 KB needs $\lceil 262{,}144/1023 \rceil = 257$ index blocks. A script built every tree with $N$ from 2 to 5 and $k$ from 0 to 4, and confirmed the leaf count $N^k$, that the leaves are distinct, the index-block count, and the base-$N$ digit rule for every leaf.

## Maximum file size of an inode
<!-- topics: os-file-systems.unix-inode, os-file-systems.indexed-allocation -->

**Claim.** An inode with $n_d$ direct pointers and one single-, one double- and one triple-indirect pointer, with $N = B/p$, describes a file of at most

$$S_{\max} = \bigl(n_d + N + N^2 + N^3\bigr) \times B$$

bytes. A pointer the inode lacks drops its term, and $m$ pointers of the same level contribute $m$ times the term. A fully allocated file also has at most $2^a$ data blocks when block addresses have $a$ bits, so the smaller of $S_{\max}$ and $2^a \times B$ applies; the free space on the disk is a further bound.

**Proof.** The direct pointers reach $n_d$ data blocks, and by the previous section the three indirect pointers reach $N$, $N^2$ and $N^3$. Each data block of the file has one place in this layout, so the counts add, and each data block carries $B$ bytes of the file. For the address bound, a fully allocated file of $k$ data blocks uses $k$ different disk blocks, each named by a different $a$-bit address, so $k \le 2^a$. A sparse file, whose holes have no blocks, can have a logical size beyond the address bound but never beyond the layout bound.

**GATE use.** This is the most common file-system NAT: the layout is given and the size is asked in KB, MB or GB. The traps are leaving out the direct blocks, using the pointer size in bits, mixing $2^{10}$ with $10^3$, and missing the address or disk bound when the question gives one; when a question adds a disk size that is far larger, it expects the layout bound.

**Check.** 4 KB blocks with 4-byte pointers and 12 direct pointers: $(12 + 1024 + 1024^2 + 1024^3) \times 4096 = 4{,}402{,}345{,}721{,}856$ B, which is 48 KB + 4 MB + 4 GB + 4 TB. Without the triple-indirect pointer the same inode reaches 1,049,612 blocks, 4,299,210,752 B $\approx 4.004$ GB. 1 KB blocks, 4-byte addresses, 12 direct pointers and one single-indirect pointer: $12 + 256 = 268$ KB. 512-byte blocks, 8-byte addresses, 10 direct pointers, one single and one double: $10 + 64 + 4096 = 4170$ blocks, which is 2,135,040 B = 2085 KB. 128-byte blocks with 8-byte addresses, 8 direct pointers, one single and one double: $N = 16$ and $(8 + 16 + 256) \times 128 = 35{,}840$ B = 35 KB, even on a 300 GB disk. 1 KB blocks with 16-bit addresses: the layout allows $(12 + 512 + 512^2 + 512^3)$ KB $\approx 128.25$ GB, but $2^{16}$ blocks of 1 KB cap a fully allocated file at 64 MB.

## From a byte offset to the disk reads through an inode
<!-- topics: os-file-systems.inode-access-count, os-file-systems.unix-inode -->

**Claim.** The byte at offset $x$ of a file with block size $B$ lies in logical block

$$i = \left\lfloor \frac{x}{B} \right\rfloor$$

at position $x \bmod B$. With $n_d$ direct pointers and $N$ pointers per index block, blocks $0$ to $n_d - 1$ are direct (level $\ell = 0$), the next $N$ go through the single-indirect pointer ($\ell = 1$), the next $N^2$ through the double ($\ell = 2$) and the next $N^3$ through the triple ($\ell = 3$). For $\ell \ge 1$, block $i$ is entry $j = i - n_d - \sum_{m=1}^{\ell-1} N^m$ of its range, and the entries to follow are the $\ell$ base-$N$ digits of $j$; a direct block $i$ is named by direct pointer $i$. With the inode in memory and no index block cached, reading that byte takes

$$R = \ell + 1$$

disk reads, plus one if the inode must be read first. Reading the first $m$ blocks in order, with each index block kept in memory once read, costs $m$ data reads plus one read per index block used.

**Proof.** Dividing $x$ by $B$ gives $x = iB + r$ with $0 \le r \le B - 1$, and logical block $i$ holds bytes $iB$ to $iB + B - 1$. The inode deals logical blocks out to its pointers in order, direct ones first, so the ranges are consecutive and block $i$ falls in exactly one; subtracting the sizes of the earlier ranges gives its position $j$ in its own range, and the previous section turns $j$ into the entries to follow. On the path to a level-$\ell$ data block, the address of each index block is stored only in its parent (the inode or the index block above), so the $\ell$ index blocks must be read one after another before the data block: $\ell + 1$ reads, and no fewer. When index blocks stay cached, a sequential read fetches each of them once.

**GATE use.** NAT questions give an offset and ask for the number of disk reads. The traps are off-by-one errors at a range boundary (with 12 direct pointers, block 12 counted from 0 is the first single-indirect block), forgetting the read of the inode or of directory blocks when the question says they are not in memory, and charging the index blocks again for every block of a sequential read.

**Check.** 4 KB blocks, 4-byte pointers, 12 direct pointers: offset $5 \times 2^{20}$ is in block $5 \times 2^{20}/2^{12} = 1280$. The direct range is blocks 0–11 and the single-indirect range 12–1035, so block 1280 is entry $j = 244$ of the double-indirect range: entry 0 of the double-indirect block, then entry 244 of the index block it names, so 3 reads. Offset 100,000 is byte 1,696 of block 24, which takes 2 reads. Blocks 11, 12, 1035, 1036, 1,049,611 and 1,049,612 take 1, 2, 2, 3, 3 and 4 reads. Reading the first 1280 blocks in order costs $1280 + 3 = 1283$ reads, the three index blocks being the single-indirect block, the double-indirect block and its first child. A script built inodes over a simulated disk, with $(n_d, N)$ equal to (2, 3), (3, 2) and (12, 4), and for every logical block reached the right data block in exactly $\ell + 1$ block reads.

## Contiguous, linked and FAT allocation: reads, block counts and table size
<!-- topics: os-file-systems.contiguous-allocation, os-file-systems.linked-allocation, os-file-systems.fat, os-file-systems.access-methods -->

**Claim.** Count logical blocks from 0, so the $k$-th block of a file is block $k - 1$.

1. Contiguous allocation: block $i$ is disk block $\text{start} + i$, one read for any $i$.
2. Linked allocation, where each block holds a $p$-byte pointer to the next and the directory entry holds only the first block's address: reaching block $i$ takes $i + 1$ disk reads (the $k$-th block takes $k$), and a file of $S$ bytes needs $k = \left\lceil \frac{S}{B - p} \right\rceil$ blocks. If the entry also holds the last block's address, the last block takes 1 read and every other block still takes $i + 1$.
3. A FAT keeps those pointers in a table with one entry of $e$ bytes for every block of the volume, so $S_{\text{FAT}} = n \times e$ whatever files exist. With the table cached, reaching block $i$ takes $i$ lookups in memory and one disk read; uncached, the walk also reads the FAT blocks it passes through. When the FAT is stored on the same disk of $n$ blocks, and nothing else takes space, the largest file is $S_{\max} = \left(n - \left\lceil \frac{n e}{B} \right\rceil\right) \times B$ bytes.

**Proof.** (1) is arithmetic on the start address. (2) When the directory entry holds only block 0's address, the address of block $i \ge 1$ is stored only inside block $i - 1$, so block $i$ cannot be fetched before block $i - 1$ has been read; by induction blocks $0, 1, \dots, i$ are all read, and following the chain reads exactly these, $i + 1$ in all. A last-block address in the entry is a second copy of one address, so it shortens only the walk to the last block, to 1 read. Each block carries $B - p$ bytes of data, so $k$ blocks hold $S$ bytes exactly when $k(B - p) \ge S$, and the smallest such $k$ is $\lceil S/(B - p) \rceil$. (3) The table describes every block, allocated or free (a free block's entry is 0), so it has $n$ entries regardless of the files. A file's chain is the same as under linked allocation, but its links are table entries: with the table in memory, block $i$'s address is found after $i$ lookups and only the data block is read. The walk is still $O(i)$; only the disk reads go away. An entry of $w$ bits can name at most $2^w$ clusters, which caps the volume: FAT16 with 32 KB clusters can cover at most $2^{16} \times 32$ KB = 2 GB. The table's $n e$ bytes occupy whole blocks, at least $\lceil n e / B \rceil$ of them since a block holds $B$ bytes, and a block given to the table cannot hold file data; the other $n - \lceil n e / B \rceil$ blocks can all go to one file, which gives $S_{\max}$.

**GATE use.** MCQs compare the methods on direct access (contiguous 1 read, indexed a few index reads, FAT an in-memory walk, linked $O(k)$ disk reads) and on fragmentation (only contiguous allocation has external fragmentation; all of them waste part of a file's last block). NAT questions ask for the FAT size or the reads needed to reach a block. The traps are calling FAT access $O(1)$, using $B$ instead of $B - p$ for the block count under linked allocation, and confusing the $k$-th block with block $k$.

**Check.** The 50th block of a file is block 49: 50 reads under linked allocation, 49 lookups and 1 read with a cached FAT, 1 read under contiguous allocation. A 1 MB file in 1 KB blocks with 4-byte pointers needs $\lceil 2^{20}/1020 \rceil = 1029$ blocks under linked allocation and 1024 with a FAT. A 4 GB volume of 4 KB clusters with 4-byte entries has $2^{20}$ entries, so a 4 MB FAT, against a 128 KB bit vector: 32 times smaller, one bit per block against 32. The wrong answers 1 MB and 32 MB come from taking an entry as 1 byte or as 32 bytes. 2 GB of 4 KB clusters gives a 2 MB FAT. A $100 \times 10^6$ B disk with $10^3$ B blocks and 4-byte entries has $10^5$ blocks and a $4 \times 10^5$ B FAT filling 400 blocks, so the largest file is $99{,}600 \times 10^3$ B $= 99.6 \times 10^6$ B; at $200 \times 10^6$ B the same layout gives $199.2 \times 10^6$ B. A script walked 300 random chains on a simulated disk, finding $i + 1$ reads under linked allocation, $i$ lookups through the FAT and 1 read for the same file stored contiguously, for every block, and checked the block-count formula on 2,000 random cases.

## Free-space maps: bit vector size, first free block and the alternatives
<!-- topics: os-file-systems.free-space-management -->

**Claim.** A bit vector has one bit per block: $n = C/B$ bits, which is $n/8$ bytes, whatever the number of free blocks. If bit 1 means free and the map is read in $w$-bit words, the first free block is

$$w \times (\text{number of all-zero words before it}) + (\text{position of the first 1 in the next word}),$$

found with at most $\lceil n/w \rceil$ word tests. A linked free list costs no extra space, but taking $k$ blocks from it reads $k$ blocks. Grouping, with $N = B/p$ addresses in each group block ($N - 1$ free blocks and then the next group block), takes $\lceil k/(N - 1) \rceil$ reads when the group blocks are kept for the list, and $\lceil k/N \rceil$ when each group block is handed out as well once its list has been read into memory. Counting stores one (start, length) pair per run of free blocks, and there are at most $\lceil n/2 \rceil$ runs.

**Derivation.** The map has an entry per block, so its length is $n$ bits whether a block is free or not. Scanning word by word, an all-zero word holds no free block and is passed over with one test; the first nonzero word contains the first free block, at its first 1 bit, and the blocks before that word number $w$ times the words passed over. Galvin gives the block number in this form. A free list stores each next-pointer inside the free block itself, so learning the next free block means reading the current one: one read per block taken. One read of a group block hands over its $N - 1$ listed free blocks at once, and $N$ blocks if the group block itself, now free and copied into memory, is handed out too; $k$ blocks then need the stated number of reads. Every run of free blocks except possibly the last is followed by an allocated block, so $r$ runs occupy at least $2r - 1$ blocks, which gives $r \le \lceil n/2 \rceil$; counting is compact when there are few long runs and wasteful when free and allocated blocks alternate.

**GATE use.** NAT questions ask for the size of the bit vector; MSQs ask what each method costs. The traps are dividing by 8 twice, decimal units, believing the size depends on the free space, and the convention for which bit value means free (the question states it).

**Check.** A 64 GB disk of 8 KB blocks has $2^{36}/2^{13} = 2^{23}$ blocks, so the vector is $2^{23}$ bits $= 2^{20}$ bytes $= 1024$ KB; 1 GB of 4 KB blocks needs 32 KB, and 4 GB of 4 KB blocks 128 KB. With 32-bit words, if words 0 to 2 are all zero and the first 1 of word 3 is at position 5, the first free block is $32 \times 3 + 5 = 101$, found after 4 word tests. With 4 KB blocks and 4-byte addresses one group block lists 1023 free blocks, so taking 5000 blocks costs 5 reads under either policy, against 5000 from a free list. The two policies first differ at 1024 blocks, which take 2 reads when group blocks are kept and 1 when they are handed out, and above 5000 they next differ at 5116 blocks, 6 reads against 5. Three free runs cost $3 \times 8 = 24$ bytes of (start, length) pairs against 32 KB for the map of a 1 GB disk of 4 KB blocks, but alternating free and allocated blocks on that disk give $2^{17}$ runs, 1 MB of pairs, 32 times the bit vector. A script compared the word formula with a bit-by-bit scan on 3,000 random maps and checked the bound on runs on 2,000 more.

## Block size: internal fragmentation against metadata and transfer speed
<!-- topics: os-file-systems.block-size-and-recovery -->

**Claim.** A file of $S$ bytes occupies $\lceil S/B \rceil$ blocks and wastes $\lceil S/B \rceil B - S$ bytes, between 0 and $B - 1$, in its last block; if $S \bmod B$ is equally likely to take each value, the mean waste is $(B - 1)/2 \approx B/2$ per file. Multiplying the block size by $m$ therefore multiplies the expected waste by about $m$. It divides the bit vector ($C/B$ bits) and the number of pointers a file needs ($\lceil S/B \rceil$) by about $m$, and for an inode with a triple-indirect pointer it multiplies the layout bound $S_{\max}$ by nearly $m^4$, because $(n_d + N + N^2 + N^3)B$ with $N = B/p$ grows like $B^4/p^3$. Each read pays the seek and the latency once, so at transfer rate $r$ the fraction of the access time spent transferring, $\frac{B/r}{T_{\text{seek}} + T_{\text{rot}}/2 + B/r}$, rises with $B$. A cluster of $m$ blocks behaves like one block of $mB$ bytes.

**Derivation.** The last block holds the remaining $S \bmod B$ bytes, or a full block when the remainder is 0, so the waste is $(B - S \bmod B) \bmod B$. As $S \bmod B$ runs over $0, \dots, B - 1$ the waste runs over the same set, whose mean is $(B - 1)/2$. The bit vector and the pointer count are $C/B$ and $\lceil S/B \rceil$, both inversely proportional to $B$ up to rounding. Substituting $N = B/p$ gives $S_{\max} = n_d B + B^2/p + B^3/p^2 + B^4/p^3$, whose last term dominates once $B/p$ is large. In the transfer fraction the overhead in the denominator is fixed while the transfer term grows with $B$, so the fraction increases towards 1. Tanenbaum (Modern Operating Systems) plots the two effects against the block size: the data rate rises while the space efficiency falls.

**GATE use.** MCQs ask what follows from a larger block size. Internal fragmentation grows, and so do the maximum file size, the transfer efficiency and the data reached per pointer; the bit vector and the index overhead shrink; indexed allocation still has no external fragmentation. The trap is reversing any one of these.

**Check.** Going from 1 KB to 8 KB blocks raises the mean waste from 511.5 B to 4095.5 B per file, averaged over all remainders; the bit vector of a 64 GB disk falls from 8 MB to 1 MB, and a 1 MB file needs 128 pointers instead of 1024. With 4-byte pointers and 12 direct pointers, $S_{\max}$ grows from about 16.06 GB to about 64.03 TB, a factor of about 4082, just below $8^4 = 4096$. Those are layout bounds. Read as 32-bit block addresses, the pointers cap a fully allocated file at $2^{32} \times 8$ KB = 32 TB, below the 64.03 TB layout bound, while with 1 KB blocks the cap of 4 TB lies far above 16.06 GB. On the disk of the geometry section (5 ms seek, 4.167 ms latency, 3.75 MB/s), a 1 KB read spends 2.76% of its time transferring and an 8 KB read 18.52%.

## Link counts: when a delete frees a file, and why cycles need garbage collection
<!-- topics: os-file-systems.links, os-file-systems.directory-structures -->

**Claim.** Treat directories and files as nodes, with an edge from a directory to each node that one of its entries names, not counting the entries "." and ".." or symbolic links; the link count of a node is its number of incoming edges. Removing an entry deletes its edge and decrements the count, and a node whose count reaches 0 is freed, a freed directory losing its own entries in turn. A file that a process still has open is freed only at its last close and is live but unreachable until then; assume below that no unlinked file is open. If the graph is acyclic, this frees exactly the nodes that are no longer reachable from the root. If cycles are allowed, a cycle cut off from the root keeps every count at least 1 and is never freed, so a general graph needs garbage collection: mark everything reachable from the root, then free the rest. A symbolic link stores a path and adds no edge, so it dangles once that path stops existing, while a hard link keeps its node alive.

**Proof.** A freed node keeps no edges, so every edge joins two live nodes and everything reachable from the root is live. Conversely, after every removal each live node other than the root has count at least 1, because with no unlinked file open a node is freed as soon as its count is 0. Suppose a live node $v_0$ is unreachable. It has an incoming edge from a live node $v_1$, which is unreachable too, or $v_0$ would be reachable; $v_1$ has an incoming edge from a live unreachable $v_2$, and so on. The graph is finite, so the walk $v_0, v_1, v_2, \dots$ repeats a node, and the stretch between the repeats is a cycle, impossible in an acyclic graph. Hence the live nodes are exactly the reachable ones. With a cycle, two directories $X$ and $Y$ that contain each other keep counts of at least 1 after the root's entry for $X$ is removed, though neither is reachable. Unix avoids the problem by forbidding hard links to directories, so the directories form a tree and only files are shared, which keeps the graph acyclic; rename refuses to move a directory into its own subtree, which would also close a cycle, and rmdir removes only empty directories, which takes care of "." and "..".

**GATE use.** MSQs on links: a hard link raises the count and keeps the data alive after the original name goes; a symbolic link has its own inode, can cross file systems and point to directories, and dangles when its target goes. MCQs on directory structures ask why a general graph needs garbage collection. The trap is assuming that deleting the original name deletes the data while a hard link remains.

**Check.** For /a/f with a hard link /b/h and a symbolic link /c/s storing the path /a/f, removing /a/f lowers the count from 2 to 1, so /b/h still reaches the data while /c/s names a path that no longer exists. A script ran 2,000 random histories of creations, removals and hard links that keep the graph acyclic, and after every step the live nodes were exactly those reachable from the root. In the two-directory cycle both counts stayed at 1 after the root's entry was removed, with neither directory reachable.
